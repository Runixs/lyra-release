Engine

엔진은 OS 계정 하나에 하나만 도는 lyra-daemon입니다. 앱 자료와 SQLite 장부의 유일한 기록자이고, Session, 터미널, 워크스페이스, Git 같은 모든 기능 연산이 여기서 결정됩니다. 앱의 sidecar와 명령줄 lyra는 엔진의 손님입니다. 손님은 저장소를 직접 열지 않습니다. PTY와 에이전트 자식은 엔진이 직접 쥐지 않고 keeper에 맡깁니다.

어디서 도는가

섹션 제목: “어디서 도는가”

실행 파일은 lyra-daemon(apps/daemon의 얇은 조립과 crates/lyra-daemon의 판단)이고, 엔진으로 돌 때의 인자는 정확히 --engine 하나입니다. 업데이트가 띄운 엔진은 --engine 뒤에 전환 번호 표지를 하나 더 받습니다. 그 밖의 모양은 모르는 인자로 보고 코드 2로 거절합니다.

엔진은 계정의 고정 런타임 폴더 <account home>/.lyra/runtime/ 아래 engine/을 자기 폴더로 씁니다. 기능 저장소 home.sqlite와 logs/home.log가 그 안에 있습니다. 폴더 전체는 폴더가, 표는 home.sqlite가 설명합니다.

누가 언제 시작하고 끝내는가

섹션 제목: “누가 언제 시작하고 끝내는가”

찾기와 띄우기

섹션 제목: “찾기와 띄우기”

앱에서는 sidecar가 먼저 엔진을 찾습니다. 엔진 폴더의 메타 파일 home-runtime.json과 단일 인스턴스 잠금 home.lock을 읽어 상태를 정합니다.

상태 뜻
running 떠 있고 붙었습니다.
starting 잠금은 쥐어졌고 메타가 없습니다. 뜨는 중입니다.
stale 메타는 있으나 듣는 쪽이 없습니다.
unreachable 떠 있는 듯한데 붙지 못했습니다. 이유 코드가 따라옵니다.
not-running 떠 있지 않습니다.

엔진이 없으면 sidecar가 로그인 문맥에서 띄웁니다. macOS에서는 사용자의 gui/<uid> 영역에 launchd 작업을 올리고, Windows에서는 이미 로그인 안에서 돌고 있는 시작기(sidecar, 명령줄, 엔진, keeper)가 CreateProcessW로 창 없이 시작기의 작업 묶음 밖에 프로세스를 직접 만들어 --engine을 실행합니다. 그래서 앱이 끝나도 엔진은 남습니다. 로그인 위치에서 띄운 엔진만 OS 자격 증명 저장소에 필요한 증거를 가집니다. SSH로 들어온 셸에서 띄운 엔진이 이미 있고 일이 0이면, sidecar는 그것을 증거와 함께 멈추고 로그인에서 다시 띄웁니다. 일이 남아 있거나 일의 수를 모르면 그대로 둡니다.

lyra daemon start는 로그인 시작기를 쓰지 않습니다. 셸에서 엔진을 터미널 없이 떼어 띄우고, 그 프로세스가 이 계정의 엔진으로 답할 때까지 기다립니다. 터미널 없는 SSH 로그인에서도 같습니다. 엔진의 메타 파일(home-runtime.json)이 띄운 PID를 적을 때까지는 아직 시작하는 중으로 보고, 처음 시작이라 엔진 폴더가 아직 없거나 메타 파일을 읽지 못하거나 이 계정 전용이 아니어도 거절하지 않습니다. 270초 한도가 끝까지 PID를 적지 않는 시작을 끝냅니다. PID가 적힌 뒤에 신원이 없거나 이 계정의 것이 아니면 거절합니다(crates/lyra-cli/src/native_start.rs). 멈춤을 받은 엔진은 도메인이 닫힌 뒤 대화 쪽이 쥔 쓰기 권한을 놓아 멈춤에 답하고, keeper와의 연결이 끝날 때도 같이 놓습니다(apps/daemon/src/authority/engine.rs).

시작 순서

섹션 제목: “시작 순서”

엔진 프로세스가 시작해서 서비스를 시작하기까지 전체 한도는 240초입니다(ENGINE_START_WITHIN). 그 앞의 OS 기동까지 합친 시작기의 한도는 270초입니다(START_LIMIT). 한 단계도 이 한도를 넘기지 못합니다.

  1. 종료 신호 처리기를 먼저 올립니다. 끝점이 생기기 전에 이미 멈출 수 있어야 하기 때문입니다.
  2. 계정 레이아웃을 확인하고 쓰기 잠금을 잡습니다(DaemonStart, 아래).
  3. 이 빌드의 프로그램 파일을 확인해 이미지를 자리에 둡니다(ImageStaging).
  4. 계정의 keeper가 있는지 보고, 없으면 같은 위치(로그인 또는 백그라운드)에서 띄웁니다(KeeperStart).
  5. keeper가 이 엔진을 주인으로 게시할 때까지 기다린 뒤, 검증된 개인 연결을 엽니다(KeeperLink).
  6. 저장소를 열고 손님 끝점을 묶습니다(AppAssembly). 메타 파일 home-runtime.json은 끝점을 듣기 시작한 뒤에 쓰고, 깨끗이 끝날 때 자기 것일 때만 지웁니다.

단계는 start-progress 사건으로 sidecar와 화면에 전해집니다. 시작이 실패하면 닫힌 코드 한 줄을 계정 폴더의 logs/engine-start.log에 남깁니다. 로그인 시작기와 떼어 띄운 시작은 표준 오류를 버리기 때문입니다. 단계 표시는 logs/engine-start-progress.json에 따로 게시합니다. 계정 폴더가 아직 없으면 아무것도 쓰지 않습니다.

하나만 도는 규칙

섹션 제목: “하나만 도는 규칙”

잠금이 둘 있습니다.

  • 쓰기 잠금: engine/control/engine.lock. 쥔 프로세스만 기록자입니다. 이미 다른 기록자가 살아 있으면 새 프로세스는 기록자가 되지 못하고 engine-not-active로 끝납니다. 그 기록자가 스스로 끝나지 않는 보존 엔진이면 engine-held-by-retained-engine으로 그 PID를 이름으로 알려, 사람이 끝낼 수 있게 합니다.
  • 손님 끝점 잠금: engine/home.lock. 이 잠금을 쥔 뒤에야 끝점 파일을 만들고, 남은 소켓 파일을 지워도 됩니다. 1초 동안 100ms 간격으로 다시 시도한 뒤에도 못 쥐면, 그 엔진에 손님으로 붙어 보고 붙으면 AlreadyRunning(코드 3), 못 붙으면 LockHeldWithoutRuntime(코드 4)으로 끝납니다.

계정을 처음 쓰는 초기화도 init.lock으로 한 번에 하나만 합니다.

끝나는 길

섹션 제목: “끝나는 길”
  • 종료 신호: Unix는 SIGTERM과 Ctrl-C, Windows는 Ctrl-C입니다. SIGHUP은 멈춤으로 보지 않고 읽지 않고 버립니다.
  • 사람의 멈춤: lyra daemon stop. 일이 남아 있거나 일의 수를 모르면 거절합니다. 앱이 설치된 컴퓨터에서는 아예 거절합니다. 이 명령은 서버나 WSL처럼 앱이 없는 컴퓨터를 위한 것입니다.
  • 엔진은 멈춤 끝점(engine/control/stop.sock, Windows는 파이프)을 따로 열고, 기록된 keeper만 멈춤을 청할 수 있습니다. 멈춤은 쓰기 잠금을 놓은 뒤에 답합니다.
  • 앱의 업데이트는 엔진을 멈추고 새 엔진을 띄웁니다(업데이트 생애).

앱을 닫아도 엔진은 끝나지 않습니다.

누구와 말하는가

섹션 제목: “누구와 말하는가”
  • 손님: 같은 사용자만 붙습니다. 소켓은 사용자 전용 폴더 안에 있고, 받은 연결의 상대가 이 OS 사용자가 아니면 첫 바이트를 읽기 전에 끊습니다. 메타 파일의 토큰을 hello에 실어 인사합니다. 앱의 sidecar는 desktop.sock(main 전용 연산을 받음), 명령줄은 home.sock으로 붙습니다. Windows는 이름 붙은 파이프를 씁니다.
  • keeper: 엔진이 먼저 붙습니다. Session, PTY, 워크스페이스, Git, 환경 탐지 호출은 keeper의 work.sock으로 가고, 개인 끝점 keeper.sock에는 실행 클라이언트 연결만 흐릅니다. 두 소켓은 계정 폴더의 keeper/ 안에 있습니다.

무엇을 지니는가

섹션 제목: “무엇을 지니는가”

엔진은 기능 저장소 home.sqlite를 쥐고, 알림, 상태 집계, 연결(Jira · GitHub 등) 상태를 메모리에 둡니다. 엔진 폴더의 로그는 logs/home.log입니다.

OS마다 다른 자리: lyra-platform

섹션 제목: “OS마다 다른 자리: lyra-platform”

macOS와 Windows가 다르게 구는 자리는 lyra-platform 한 곳에 모여 있고, 다른 crate는 “이 기계에서는 어떻게 하지?“를 직접 따지지 않고 여기에 묻습니다. 묻는 서랍은 넷입니다: 파일(실행 위치 목록, 경로 만들기와 비교, 권한), 창(창 틀 값, 단축키 조합, 창 명령의 닫힌 모양), 프로세스(무리에 넣어 띄우기, 띄운 목록, 트리 끊기, 터미널), OS 서비스(자격 증명 저장소 손잡이, 전송 수단).

crate는 두 층입니다. 판단 층은 터널, daemon, 창, 자식 없이 돌고 대부분이 여기 있습니다. OS 층은 sys::PlatformSys 뒤에 있습니다. src/sys/ 밖에는 cfg(target_os · cfg(windows · cfg(unix가 한 줄도 없어야 하고, tests/pure.rs가 이것을 검사합니다. 위 “찾기와 띄우기”의 로그인 시작기(macOS의 launchd, Windows의 CreateProcessW)도 이 crate의 sys/login_session/ 아래에 있습니다. 비밀 값은 이 crate가 아니라 Credentials의 lyra-credential-vault가 가집니다.

모듈 한눈에

섹션 제목: “모듈 한눈에”

엔진의 기능은 crates/lyra-app/src/engine/의 모듈들이 나눠 맡습니다. 각 모듈의 자세한 설명은 기능 쪽에 있고, 여기서는 어느 쪽으로 가면 되는지만 가리킵니다.

하는 일 모듈 자세한 곳
Session의 열기, 대화, 중단, 이어하기 sessions, producer*, session_*, turn, conversation*, transcript_cards Sessions
받은 요청과 알림 inbox, notices, terminal_inbox Inbox
오케스트레이션 dispatch, supervision, worker_identity, wait_receipts Orchestration
워크플로 workflows Workflows
이슈와 연결 workspace_issues, connections Issues
프로젝트와 워크스페이스 projects, project_*, workspace*, explorer_memory, lyra_workspaces Projects
터미널 terminal*, process_status Terminals
시리얼 serial Serial
검색 search Search
업데이트 update_activity, daemon_adoption, daemon_restart, engine_activation Updates
상태와 사용량 status_channel, usage* Status
WSL wsl, wsl_control WSL

이 표는 모듈의 큰 줄기만 모았습니다. 모든 crate와 모듈이 어느 쪽에 속하는지는 crate 목록이 정합니다.

멈추면 어떻게 되는가

섹션 제목: “멈추면 어떻게 되는가”
  • 엔진이 죽거나 끝남: 손님은 연결을 잃고, sidecar가 위의 규칙대로 다시 붙거나 다시 띄웁니다. keeper와 그 PTY는 계속 돌고, 엔진이 다시 올라오면 keeper가 새 엔진을 주인으로 게시합니다.
  • keeper가 안 올라옴: 엔진은 시작에 실패합니다(keeper-start-failed 계열). 이유는 logs/keeper-start.log에 남고, 앱이 그것을 읽어 화면에 보입니다.
  • 일이 남은 채 업데이트: quiet 방식의 멈춤(update.arm)은 대화가 답하는 중이거나 명령이 도는 중이면 엔진이 busy로 거절합니다. Update now의 멈춤 교환은 60초 안에 끝나야 하고(UPDATE_WITHIN), 넘으면 끝없이 기다리지 않고 거절합니다.

설계와 다른 점
