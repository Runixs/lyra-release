Server daemon

서버의 lyra-daemon은 서버나 WSL 배포판에서 도는 lyra-daemon입니다. 같은 실행 파일이지만 이 컴퓨터의 엔진과 달리 serve --socket <path> --remote로 돕니다. 이 컴퓨터의 엔진이 SSH 연결 하나를 열고, 그 위에서 서버의 lyra-daemon에 붙어 Session의 에이전트와 셸 같은 일을 서버에서 시킵니다. 서버 쪽에는 앱도 데이터 저장소도 없고, 일을 시키는 쪽은 언제나 이 컴퓨터의 엔진입니다.

어디서 도는가

섹션 제목: “어디서 도는가”

설치 자리는 서버 사용자 홈 아래 .lyra/daemon/입니다. 버전마다 폴더가 따로 있고, 실행 중인 상태 폴더는 프로토콜별로 따로 있습니다.

폴더 무엇
<home>/.lyra/daemon/<version>-<target>/ 설치된 실행 파일 lyra-daemon과 lyra(그리고 같은 대상의 보조 파일)
<home>/.lyra/daemon/protocol-<protocol>-<target>/ 실행 중인 daemon의 상태: 끝점 daemon.sock, 인스턴스 기록 daemon-instance.json, daemon.log
  • <version>은 daemon의 제품 버전, <protocol>은 lyra-link-protocol의 프로토콜 버전입니다(지금은 0.2.6). 제품 버전이 달라도 프로토콜이 같으면 같은 상태 폴더를 씁니다.
  • <target>은 서버에서 uname -sm을 읽어 정합니다. Linux는 x86_64-unknown-linux-musl 또는 aarch64-unknown-linux-musl, macOS는 x86_64-apple-darwin 또는 aarch64-apple-darwin입니다. 그 밖의 값은 추측하지 않고 link-daemon-target-unsupported로 끝납니다. macOS 서버용 패키지는 배포하지 않으므로, macOS 서버에 새로 설치하려 하면 link-daemon-macos-server-unsupported로 거절합니다. 이 버전이 이미 돌고 있는 서버는 그대로 씁니다.
  • 끝점 경로가 100바이트를 넘으면 소켓만 /tmp/lyra-<uid>/protocol-<protocol>-<target>.sock으로 옮깁니다. 인스턴스 기록은 그대로 상태 폴더에 둡니다.
  • Windows 서버는 같은 모양을 %USERPROFILE%\.lyra\daemon\에 만들고, 끝점은 SID가 들어간 이름 붙은 파이프 \\.\pipe\lyra-daemon-remote-protocol-<protocol>-<target>-<SID>입니다.

누가 언제 시작하고 끝내는가

섹션 제목: “누가 언제 시작하고 끝내는가”

올리기와 띄우기

섹션 제목: “올리기와 띄우기”

이 컴퓨터의 엔진 안의 lyra-link가 SSH 연결을 열 때마다 서버를 새로 풀어서 봅니다. WSL 배포판은 SSH 대신 wsl.exe 자식 하나가 같은 명령을 돌리다가 attach로 바뀝니다(WSL).

  1. 탐색: 서버에서 한 번의 명령으로 $HOME, uid, uname -sm을 읽습니다. 모양이 다르면 원문을 싣지 않고 설치 실패로 끝냅니다.
  2. 확인: 서버의 버전 폴더에 이 버전의 설치 완료 표시(.installed)가 있으면 그 서버는 이미 이 버전이 깔린 것으로 보고, 앱의 패키지를 기다리지도 서버 파일의 지문을 앱 패키지와 견주지도 않습니다. 서버가 자기 설치 기록으로 스스로 확인한 뒤 보조 파일, 띄우기, 붙기로 갑니다. 표시가 없으면 설치가 필요합니다.
  3. 패키지 준비: 앱 설치본과 업데이트에는 서버 패키지가 없습니다. 설치가 필요하면 이 컴퓨터의 엔진이 업데이트를 받는 곳에서 이 버전의 서버 패키지를 내려받아 엔진 폴더의 server-packages/<version>/에 두고 씁니다(crates/lyra-app/src/server_package.rs). 배포하는 패키지는 Linux x86_64 · aarch64와 Windows x64 셋이고 macOS는 없습니다. 버전마다 내려받기 일은 하나이고, 10초 동안 닿는지 먼저 보고 파일을 받아 디스크에서 다시 확인한 뒤 이름을 바꿔 둡니다. 패키지 하나에 10분까지 쓰고, 연결 하나는 자기 대상의 패키지를 120초까지 기다립니다. 이 동안 연결 단계는 버전 확인입니다. 패키지 안의 서명된 코드 매니페스트가 이 빌드에 굳힌 릴리스 키로 서명되었고 이 빌드의 버전, 빌드, 대상과 서버의 대상을 적었는지, 파일마다 길이와 SHA-256이 맞는지 봅니다. 서명 없는 SHA256SUMS.txt는 읽지 않습니다. 네트워크가 없으면 사람이 릴리스 페이지에서 받은 패키지를 server-packages/incoming/에 넣어 둘 수 있고, 이것도 같은 확인을 거칩니다. 이 버전과 가장 새 다른 버전 하나만 남기고 나머지는 지웁니다. 얻지 못하면 link-daemon-package-unavailable, 확인을 통과하지 못하면 link-daemon-package-unproved, 이 컴퓨터에 두지 못하면 link-daemon-package-cache-failed로 설치만 거절하고, 이 버전이 이미 돌고 있는 서버는 그대로 씁니다.
  4. 올리기: 준비한 패키지의 파일을 올립니다. 올리기는 임시 이름으로 올려 지문을 확인한 뒤 자리로 옮깁니다. 이미 쓰는 자리를 덮어쓰지 않으려고 사용 중인지 시스템 증거로 확인합니다. 30초 동안 올라간 바이트가 없으면 link-upload-stalled로 끝나고, 전체 올리기 한도는 파일 크기를 256KiB/s로 나눈 시간에 30초를 더한 값이며 60초 아래로는 내려가지 않습니다. 올리기와 띄우기는 서버의 버전 폴더에 시도의 표시를 남기기 전에 그 폴더를 잠급니다. 서버의 flock(BusyBox의 flock도 됩니다)이나 lockf로 하고, 다른 시도가 쥐고 있으면 실패 이유가 cleanup-claim-held입니다. 잠금 없이 진행하는 때는 둘입니다. 쓸 수 있는 잠금 명령이 없을 때(Linux에 flock이 없거나, macOS에 /usr/bin/lockf가 없거나, 그 밖의 OS)와, 버전 폴더들이 든 ~/.lyra/daemon/이 이 사용자 전용(700)인지 확인되지 않거나 잠금 파일이 링크일 때입니다. 명령이 있는데 실패하면 cleanup-lock-failed로 멈추고 잠금 없이 진행하지 않습니다.
  5. 띄우기: 서버에서 nohup <lyra-daemon> serve --socket <socket> --remote를 SSH가 끝나도 살아남게 띄웁니다. Windows는 sshd가 명령 채널을 닫을 때 같은 무리의 프로세스를 끊으므로, WMI Win32_Process.Create로 무리 밖에서 띄웁니다. WSL은 --remote --wsl을 더해 WSL 한가함 규칙(한 번 붙은 뒤에는 스스로 내려가지 않음, IdlePolicy::WSL)을 고릅니다.
  6. 기다림: 소켓이 준비됐는지 200ms마다 보고, 50번(10초)까지 기다립니다.
  7. 붙기: SSH 명령 채널로 lyra-daemon attach --socket <socket>을 실행하면, 그 채널의 입출력이 서버 안 소켓에 바이트 그대로 이어집니다. 첫 교환(핸드셰이크)에 5초를 줍니다.

--remote를 붙이면 daemon의 상태 폴더가 실행 파일이 놓인 폴더의 형제(protocol-…)가 되고, 서버의 에이전트가 쓰는 lyra를 이 컴퓨터의 엔진으로 이어 주는 CLI 다리가 만들어집니다(명령줄).

하나만 도는 규칙

섹션 제목: “하나만 도는 규칙”

끝점 하나는 daemon 하나만 쥡니다. 같은 끝점을 이미 다른 daemon이 쥐고 있으면 새 프로세스는 EndpointOccupied로 코드 3을 내고 끝납니다. 쥔 daemon은 끝점을 잡은 직후 자기 PID를 daemon-instance.json에 씁니다. 서버의 누가 쥐고 있는지는 그 기록의 PID를 읽고, 그 PID가 이 끝점의 소켓을 실제로 쥐고 있는지 /proc에서 확인한 뒤 실행 이미지를 읽어 압니다. 프로세스를 모두 나열하지 않습니다. 확인하지 못한 것은 unknown입니다.

끝나는 길

섹션 제목: “끝나는 길”
  • 한가함: 연결이 0이고 자식이 0인 채로 한 번이라도 붙은 뒤에는 15분, 한 번도 붙지 않았으면 60초 뒤에 내려갑니다. WSL에서 띄운 것은 한 번 붙은 뒤에는 스스로 내려가지 않고 배포판이 도는 동안 떠 있으며, 한 번도 붙지 않았으면 60초입니다.
  • 종료 요청: SIGTERM을 받으면 새 연결을 받지 않고(Draining) 자식이 끝나기를 기다립니다. 상태는 Starting, Serving, IdleCountdown, Draining, Stopped입니다.
  • 더 새로운 버전의 정리: 이 컴퓨터가 새 버전을 올린 뒤 lyra-daemon retire-older를 서버에서 실행해, 같은 사용자의 옛 버전 daemon을 멈춥니다.

누구와 말하는가

섹션 제목: “누구와 말하는가”

daemon은 SSH 채널 하나에서 논리 채널 여럿을 다룹니다. 채널 이름과 메시지는 Link에, WSL 배포판에 닿는 길은 WSL에 있습니다. 서버의 lyra-daemon은 SSH를 직접 알지 못합니다. 그저 소켓에서 연결을 받습니다.

무엇을 지니는가

섹션 제목: “무엇을 지니는가”
  • 에이전트와 셸 자식 프로세스와 그 PTY. 이 일은 이 컴퓨터의 keeper가 아니라 서버의 lyra-daemon 자신이 합니다(자식).
  • 재전송 버퍼: 채널 하나에 32MiB, daemon 전체에 256MiB까지입니다. 연결이 끊긴 사이의 출력을 다시 보내 주기 위해서입니다.
  • 인스턴스 기록과 로그, 그리고 자식 프로세스의 표식.

서버에는 이 컴퓨터의 home.sqlite 같은 저장소가 없습니다.

서버 주소록: lyra-server

섹션 제목: “서버 주소록: lyra-server”

사람이 더한 서버는 lyra-server의 주소록(ServerRegistry)이 가집니다. 이 crate는 파일, 망, 자식 프로세스를 쥐지 않습니다. 파일 servers.json의 위치는 폴더가, 연결은 Link가 설명합니다. 연결할 때마다 lyra-link가 서버 id로 이 주소록에서 대상을 새로 풀어 옵니다.

  • 서버 하나는 id, 이름, 주소(호스트와 포트), 사용자 이름, 호스트 키 정책, 인증 방식, 도달 관측, 수명 상태를 한 버전(revision)으로 묶어 가집니다. 사용자의 ~/.ssh/config의 Host 별칭을 쓰는 서버는 별칭도 가지고, 주소와 사용자 칸은 등록 때 받은 대체값입니다.
  • 호스트 키 정책은 known-only(이미 기억한 키만)와 accept-new(처음 보는 키는 기억하고 받고, 기억한 키와 다르면 거부, 기본)입니다. 검사를 끄는 값은 없습니다.
  • 인증 방식은 memory-password(지금 엔진 프로세스가 가진 SSH 비밀번호)와 credential-ref(저장소 안의 키나 암호의 참조)입니다. 비밀 값은 주소록에 없습니다.
  • 도달 관측은 unverified · reachable · unreachable이고, 그 버전의 마지막 관측일 뿐 지금 연결돼 있다는 보장이 아닙니다. 수명 상태는 active와, 삭제가 시작돼 저장소 연결을 떼기를 기다리는 deleting입니다.
  • 저장 형식은 SUPPORTED_FORMAT_VERSION 3입니다. 앞 버전으로 PREVIOUS_FORMAT_VERSION 2와 LEGACY_FORMAT_VERSION 1이 코드에 있습니다.

멈추면 어떻게 되는가

섹션 제목: “멈추면 어떻게 되는가”
  • 연결이 끊김: 서버의 lyra-daemon은 계속 돕니다. 이 컴퓨터의 엔진이 20초 계획으로 다시 붙고, 못 붙으면 실패로 드러낸 뒤 사람의 조작이나 잠 깸을 기다립니다.
  • daemon이 사라짐: 자식은 플랫폼 표식으로 고아로 잡힙니다. 같은 프로토콜의 상태 폴더를 쓰는 다음 daemon이 자기 목록을 이어 씁니다. 이 컴퓨터는 다음에 붙을 때 daemon이 있는지 확인하고 없으면 다시 띄웁니다.
  • 버전이 다름: 버전이 어긋나면 core-version-mismatch, 같은 자리에서 이 앱이 설치한 것이 아닌 다른 빌드가 돌면 daemon-other-build-running, 옛 daemon을 멈췄다는 증거를 얻지 못하면 daemon-retire-unconfirmed로 알립니다.
