Engine start and restart

이 쪽은 이 컴퓨터의 엔진이 앱 옆에서 뜨고, 끊기고, 다시 뜨는 흐름을 시간 순서로 따라갑니다. 엔진 프로세스 안의 시작 단계, 두 잠금, 종료 코드는 Engine이, 소켓과 인사는 손님 소켓이, keeper가 남기는 것은 Keeper가 설명합니다.

순서

섹션 제목: “순서”

  1. sidecar 시작. main이 lyra-desktop-sidecar를 띄우고 첫 ready 줄을 기다립니다. 상한은 300초(READY_TIMEOUT_MS)입니다. 이 기다림은 엔진 시작의 상한(270초)에 sidecar 자신의 시작 30초를 더한 값입니다. 넘으면 main이 start-timeout으로 끝내고 sidecar를 SIGKILL합니다. 이 시간 동안 화면의 요청은 main의 표에 줄을 섭니다.

  2. 업데이트 전환 확인. sidecar는 먼저 keeper가 가진 엔진 전환 기록을 읽습니다. 업데이트가 도는 중이면 250ms(RECONNECT_PAUSE) 간격으로 다시 읽으며 기다립니다. 끝났거나 전환이 없으면 다음으로 갑니다. 전환이 실패했거나 알 수 없으면 기다리지 않고 사람의 복구가 필요한 코드(engine-recovery-required, engine-update-state-unknown 등)로 멈춥니다. 전환의 길은 업데이트 생애에 있습니다.

  3. 찾기. sidecar가 엔진 폴더의 home.lock과 home-runtime.json을 읽어 상태를 정합니다(running · starting · stale · unreachable · not-running, 뜻은 Engine). not-running과 stale은 없는 것으로 봅니다. starting과 running이면 running이 될 때까지 10초(START_WITHIN) 기다린 뒤 붙습니다. unreachable이면 그 이유 코드로 실패합니다.

  4. 있는 엔진을 어떻게 하나. 붙은 엔진이 어디서 떴는지는 엔진이 스스로 말하는 것이 아니라 OS 증거(로그인 시작기가 남긴 등록 또는 OS가 둔 자리, SSH가 남긴 떼어 띄움 기록)로 읽습니다.

    증거 일의 수 결과 로그 줄
    로그인에서 떴음 상관없음 그대로 붙음 engine-attached
    로그인 밖에서 떴고 로그인 시작이 불가능함(로그인 세션이나 설치된 앱이 없음) 세지 않음 그대로 둠 engine-kept-without-login-start
    로그인 밖에서 떴음 0이 아니거나 모름 그대로 둠, 다음 앱 연결 때 다시 확인 engine-kept-busy
    로그인 밖에서 떴음 0 home.stop을 ifIdle로 보내 멈추고, 끝나고 잠금이 풀리고 끝점이 지워진 것을 본 뒤, 한가한 옛 keeper를 거두고 로그인에서 다시 띄움 engine-restarted-into-login
    위와 같은데 엔진이 멈춤을 거절함 그대로 둠 engine-kept-stop-refused

    멈춤의 끝을 확인하지 못하면(home.stop-timeout 등) 옛 엔진 옆에 새 엔진을 띄우지 않고 engine-restart-stop-unproven으로 멈춥니다. 일의 수는 Session 목록, 터미널 목록, keeper의 custody 행을 모두 읽어 셉니다. 한 쪽이라도 읽지 못하면 일이 있는 것으로 봅니다.

  5. 없는 엔진을 띄움. 사람이 멈춘 기록(engine-stopped-by-person)이 있으면 띄우지 않고 그 이유로 멈춥니다. 아니면 sidecar가 로그인 시작기를 부릅니다. macOS는 gui/<uid> 영역의 launchd 일회 작업, Windows는 CreateProcessW입니다(Engine). 시작기의 한도는 270초(START_LIMIT)이고 그 안에 엔진 프로세스의 240초(ENGINE_START_WITHIN)가 들어갑니다. 엔진 안의 단계 표시(DaemonStart → ImageStaging → KeeperStart → KeeperLink → AppAssembly)는 Engine이 설명하고, 이 쪽에서 보는 것은 그 결과뿐입니다.

  6. keeper. 엔진은 계정의 keeper가 있으면 붙고 없으면 같은 위치에서 띄웁니다. 옛 빌드의 keeper가 있으면 그대로 붙습니다. keeper를 넘겨 바꾸는 스위치(KEEPER_HANDOVER)는 꺼져 있고, 이 일은 Keeper에 있습니다.

  7. 붙기. 엔진이 home-runtime.json을 쓰고 끝점을 듣기 시작하면 sidecar가 desktop.sock에 붙어 hello에 토큰을 싣습니다. sidecar는 단계 진행(start-progress)을 logs/engine-start-progress.json에서 읽어 화면에 전하고, 마지막 단계 MetadataReady는 “sidecar가 엔진 끝점을 인증했다”는 뜻입니다. ready 줄이 main으로, 거기서 화면으로 올라갑니다.

단계마다 실패하면

섹션 제목: “단계마다 실패하면”

시작이 실패하면 sidecar의 시작 반복이 실패한 이유의 분류로 다음을 정합니다. 분류표 자체(사람이 치워야 하는 이유, 잠깐 지나가는 이유, 그 밖)는 손님 소켓에 있고 여기서는 시간 쪽만 적습니다.

상황 시작 반복이 하는 일
첫 연결(앱을 처음 켤 때) 쉬지 않고 바로 시작합니다. 사람이 멈춘 기록이 걸려 있으면 기다리지 않고 그 이유를 돌려주고, 그 기록이 사라지는 것은 사람이 시작을 누르는 곳에서 기다립니다.
연결이 끊긴 뒤 다시 붙기 250ms(RECONNECT_PAUSE)를 쉰 뒤 시작합니다.
잠깐 지나가는 이유로 실패 2초, 5초, 15초, 30초 순으로 쉬며 다시 시작하고, 마지막 뒤에도 실패하면 그 이유로 멈춥니다.
앞선 엔진이 끝나는 중이라 쓰기 잠금을 쥐고 있음(engine-held-by-ending-engine) 30초를 쉬고 다시 시작합니다. 이 경우는 실패 횟수에 세지 않아, 앞선 엔진이 얼마나 오래 끝나든 한도가 닳지 않습니다.
앞선 엔진이 스스로 끝나지 않음(engine-held-by-retained-engine) 다시 하지 않고 멈춥니다. 사람이 그 PID를 끝내야 합니다.
서비스하다 죽은 경우를 포함한 그 밖의 이유 250ms 뒤 다시 시작합니다. 한 번도 서비스하지 못한 시작이 연달아 5번이면 home.restart-throttled로 멈춥니다. 서비스에 성공하면 횟수는 0으로 돌아갑니다.
사람이 멈춘 기록이 걸림 1초(STOP_RECORD_POLL)마다 기록이 사라졌는지 보며 기다립니다.
위의 모든 시작 앱 자료 폴더 하나에서 60초에 5번이라는 창을 지킵니다(RECONNECT_LIMIT). 다 쓰면 home.restart-throttled입니다.

다시 붙는 데 성공하면 sidecar가 ready를 다시 쓰고 이어서 data-changed(전체)를 보내 화면이 목록을 모두 다시 읽게 합니다. 시작 반복이 멈추면(ready에 blocked와 이유가 실립니다) sidecar는 읽기 전용 재검사 요청만 받으며 살아 있고, 한도를 소진한 시작은 더 하지 않습니다. 앱은 ready의 blocked를 보고 막힘을 화면에 보입니다. 엔진 프로세스 자체의 실패는 닫힌 코드로 logs/engine-start.log에 남습니다.

멈춘 엔진을 다시 띄움

섹션 제목: “멈춘 엔진을 다시 띄움”

엔진이 죽는 것과 멈추는 것은 다릅니다. 죽으면 연결이 끊겨 위의 “끊긴 뒤 다시 붙기”로 갑니다. 멈춘 채 살아 있는 엔진은 연결이 끊기지 않으므로 사람이 다시 띄우는 길이 따로 있습니다.

  1. 엔진 안의 감시기(watchdog)가 일하는 스레드마다 진전을 250ms 간격으로 확인하고, 30초(STALL_LIMIT) 동안 진전이 없으면 멈춤으로 기록합니다. 감시기는 1초마다 상태 파일 state-home.<pid>.json을 새로 씁니다.
  2. 앱 main은 이 파일을 엔진과 sidecar를 거치지 않고 직접 읽습니다. 엔진이나 sidecar가 얼어도 볼 수 있어야 하기 때문입니다. 멈춤은 runtime-watchdog 사건으로 화면에 올라갑니다.
  3. 사람이 다시 띄우기를 누르면 app.restart-background가 lyra-home과 그 인스턴스를 싣고 main에 옵니다. main은 지금도 그 멈춤이 이어지는지 다시 읽어 증거를 만듭니다. 이미 끝났거나 프로세스가 바뀌었으면 home.watchdog-restart-unconfirmed로 거절합니다.
  4. main이 lyra-desktop-sidecar --restart-stalled-home을 따로 띄웁니다. 얼어 있을 수 있는 기존 sidecar와 독립된 프로세스이고, 45초 안에 끝나야 합니다. 넘으면 SIGKILL하고 home.watchdog-restart-unconfirmed입니다.
  5. 이 도우미는 증거를 확인합니다. 그 엔진의 runtimeId와 pid, 프로세스 시작 시각이 상태 파일과 같고, 상태 파일은 3초 이내에 관찰되었고, 같은 스레드의 durationMs가 30000 이상이어야 합니다. 시작 중인 엔진은 runtimeId가 starting-<pid>-<시작 시각>이고 멈춘 작업이 home.start일 때만 인정합니다. 이어서 OS에서 그 프로세스가 같은 것인지 확인하고, 프로그램 이미지가 설치된 것인지 본 뒤 멈춥니다. 마지막으로 home.lock을 쥐고 자기 runtimeId의 메타 파일을 지웁니다.
  6. 도우미는 새 엔진을 띄우지 않습니다. 끊긴 연결을 본 sidecar의 시작 반복이 위의 규칙으로 새 엔진을 띄웁니다. keeper와 터미널은 건드리지 않습니다.

서버를 선택해 둔 상태에서는 이 길이 거절됩니다. 이 길은 이 컴퓨터의 엔진만 다룹니다.

다시 시작해도 남는 것

섹션 제목: “다시 시작해도 남는 것”
  • keeper와 PTY, 에이전트: 엔진이 죽거나 멈춰 다시 떠도 keeper는 그대로 돕니다. 새 엔진이 그 keeper에 붙습니다(Keeper).
  • home.sqlite와 Session 기록: 엔진 폴더에 있고 그대로 남습니다. 열기 도중이던 Session은 Session 열기가 설명합니다.
  • 사람이 멈춘 기록: 파일로 남아 시작을 막고, 사람이 시작을 누르거나 다른 시작이 지울 때까지 갑니다.
  • 시작 실패의 닫힌 코드: logs/engine-start.log, 단계 표시는 logs/engine-start-progress.json에 남습니다(로그).
  • 남지 않는 것: 시작 반복의 실패 횟수와 60초 창은 sidecar 프로세스의 메모리에 있습니다. sidecar가 다시 떠야 처음부터 셉니다. home-runtime.json은 깨끗이 끝날 때 엔진이 지우고, 죽은 엔진이 남긴 것은 stale로 읽습니다.
