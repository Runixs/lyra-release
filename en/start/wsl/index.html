Use WSL as a server

When to use it

Section titled “When to use it”

On some PCs, Windows needs almost a second just to start one program. An agent starts a great many small programs, such as git, the shell, and various tools, so work on such a PC becomes noticeably slow. Inside WSL (a Windows feature that runs Linux inside Windows), the same work is much faster.

Keep your repositories on the WSL file system (under ~/ inside WSL). If you keep them on a Windows drive such as /mnt/c, work gets even slower. This is the way to use WSL until Lyra supports WSL directly: you register WSL as an SSH server.

Measurement (one PC as an example) Windows Inside WSL
Starting an empty program about 0.9 s under 1 ms
claude --version about 1.5 s about 0.01 s
git status about 1 s (repository on a Windows drive) about 0.003 s (repository on the WSL file system) · about 2.6 s for a repository on /mnt/c

Prepare: turn on the SSH server in WSL

Section titled “Prepare: turn on the SSH server in WSL”

Do steps 1 and 2 in PowerShell, and steps 3 to 6 inside WSL (Ubuntu).

  1. If you have no WSL and Ubuntu, install them from PowerShell and follow the prompts to choose an Ubuntu user name and password.

  2. Open Ubuntu (wsl) and check that systemd is on.

    If you get an error that systemd is not available, put these two lines in /etc/wsl.conf, run wsl --shutdown in PowerShell, and then open Ubuntu again.

  3. Install the SSH server.

  4. Windows may already have an SSH server, so use port 2222, which does not overlap.

  5. Apply the setting and turn it on. On Ubuntu 24.04 and later, ssh.socket accepts connections, and daemon-reload carries the Port from sshd_config over as it is.

    If there is no ssh.socket, as on Ubuntu 22.04, use sudo systemctl enable --now ssh and sudo systemctl restart ssh.

  6. To sign in without a password, put your Windows SSH key into WSL. If you have no key on Windows, create one first in PowerShell.

    Add the public key to the authorized_keys of WSL. (<WSL user> is your Ubuntu user name.)

    If you pass it straight from PowerShell, Windows PowerShell 5.1 puts an invisible character in front of the key and the sign-in is refused, so pass it through cmd.

  7. Try to connect from PowerShell. The first time, it asks whether you trust the server’s identity.

    If you get in without a password, the preparation is done. Leave with exit.

Add the WSL server in Lyra

Section titled “Add the WSL server in Lyra”

In Settings → Connections → Remote, click Add server. There are two ways.

Method A: add it by a Host alias from your ssh settings (recommended)

Section titled “Method A: add it by a Host alias from your ssh settings (recommended)”

If you sign in with a key, this method fits best. Lyra uses the key files named in your ssh settings and the keys in ssh-agent as they are, so you never have to enter a password in Lyra separately.

  1. Write this in the file %USERPROFILE%\.ssh\config on Windows.

  2. In Add server, choose From SSH settings, pick wsl from the list, check the Name, and click Save.

  3. Click Connect on the server row.

If your ssh settings refuse server keys they do not know (StrictHostKeyChecking), you must make the ssh connection from step 7 above once to confirm the server key, or Lyra cannot connect.

Method B: enter it manually

Section titled “Method B: enter it manually”
  1. In Add server, choose Enter manually.
  2. Enter WSL in Name, localhost (or 127.0.0.1) in Address, 2222 in Port, and <WSL user> in User, then click Save.
  3. Click Connect on the server row. For a server entered manually, a password dialog appears when you connect. Enter the password of the WSL user.
  4. Once connected, the server row shows Register SSH key. When you click it, Lyra adds the public line of your SSH key to ~/.ssh/authorized_keys in WSL, so you need no password from then on.

The password you enter in a manual setup is kept only in the memory of lyra-daemon on this computer and is not saved to disk. When lyra-daemon ends or you restart Lyra, you must enter it again. Registering the key removes this chore.

The first time you connect

Section titled “The first time you connect”
  • If Lyra has not seen the server’s identity (its host key) before, it remembers it, and from then on it checks that it is the same server.
  • Lyra uploads lyra-daemon into WSL. It goes in ~/.lyra/daemon/ in WSL, and Linux x86_64 and aarch64 are supported. So the first connection takes a little while.
  • While it connects, the step in progress appears below the server row. The first time there is a step that uploads lyra-daemon, so it takes a little while. The steps are listed in Steps shown while connecting.
  • When the server row shows Connected, you are done.

Isn’t this confusing with this computer’s localhost?

Section titled “Isn’t this confusing with this computer’s localhost?”

Even if the address is localhost, the WSL server appears in Lyra under the server name you chose (for example WSL). The name localhost is attached only to this computer (Windows). The Host label on a Project row shows the server name, and the Host choice in Add Project shows the server name together with an SSH label.

Open a Project in WSL

Section titled “Open a Project in WSL”
  1. Open Projects in the left rail and click Add project.
  2. In the Add Project dialog, choose the WSL server under Host (the server name plus SSH).
  3. In Path, enter a path inside WSL. For example: /home/<WSL user>/work/sample-app. The folder browse button shows the folders on the server. If the repository does not exist yet, you can fetch it into WSL with Clone from URL.
  4. Click Add.

Do not use /mnt/c/... paths. They are slow.

The agent programs (Claude Code, Codex, OpenCode) must be installed inside WSL. Profiles are also kept separately for each WSL distribution. In Settings → Agents, choose the distribution marked WSL in the Machines list on the left. Installing and adding a Profile work the same way as in When the agent program is not installed and Add a Profile. After that, creating a workspace and opening a Session are the same as in 2. Create a workspace.

WSL resource settings (.wslconfig)

Section titled “WSL resource settings (.wslconfig)”

.wslconfig is a Windows-side settings file that applies to all WSL on this PC. It does not exist by default. If you need it, create it yourself at %UserProfile%\.wslconfig. Lyra neither reads nor changes this file. What follows is carried over from Microsoft’s WSL guides (settings, disk space, basic commands).

The disk grows as one file

Section titled “The disk grows as one file”

  • All the files of a WSL distribution (for example Ubuntu) live in one virtual disk file called ext4.vhdx. This file is under %LOCALAPPDATA%.

  • It grows by itself as you use it, and its default maximum size is 1 TB. As repositories and build outputs pile up, the C: drive of Windows fills up by that much.

  • You can see the free space inside WSL from PowerShell like this.

  • Do not move or open the WSL files inside AppData with Windows programs. The distribution can be damaged.

Memory and CPU limits

Section titled “Memory and CPU limits”

By default, WSL can use half of the Windows memory and all logical processors. To reduce that, write the limits in .wslconfig. The values below are examples.

It shuts down by itself when idle

Section titled “It shuts down by itself when idle”

  • A WSL distribution shuts down by itself after 15 seconds of idleness (instanceIdleTimeout under [general], default 15000 milliseconds). Lyra cannot connect to a WSL that is off.

  • To keep it on, set -1. In exchange, WSL keeps holding memory.

Apply changed settings

Section titled “Apply changed settings”

After you change .wslconfig, you must shut WSL down completely and start it again for the change to apply.

wsl --shutdown shuts down all running distributions right away. The Lyra Sessions and terminals that were running inside WSL are cut as well, so finish what you are doing first.

Removing a distribution also deletes your repositories

Section titled “Removing a distribution also deletes your repositories”

wsl --unregister <distribution name> permanently deletes that distribution’s data, settings, and installed programs. The repositories you kept inside WSL all disappear with it. Before that, push the work of every repository to a remote repository.

When something goes wrong

Section titled “When something goes wrong”
  • I cannot connect. WSL may be off (It shuts down by itself when idle). Run wsl in PowerShell to start Ubuntu again. If systemd is on, the SSH service starts along with it. If the server cannot be reached, the connection ends within 10 seconds with a timeout message.
  • I cannot sign in. See When server sign-in fails or times out.
  • “The server identity key was refused.” appears. It appears when the server’s identity changes, for example when you install WSL again. Connect only after you have checked that the change is expected.
  • The Project is slow. Check whether the repository is under /mnt/c. Moving it under ~/ in WSL makes it faster.
