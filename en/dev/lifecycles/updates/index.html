Updating the app and the server daemon

This content is not available in your language yet.

이 쪽은 앱과 엔진, 서버의 lyra-daemon이 새 버전으로 바뀌는 한 번의 흐름을 시간 순서로 따라갑니다. 업데이트의 기록, 연산, 설정 키는 Updates가, 설치 폴더와 한가함 규칙은 서버의 lyra-daemon이, 엔진이 끊기고 다시 뜨는 규칙은 Engine start and restart가 설명합니다. 화면에서 하는 일은 설정의 정보 쪽에 있습니다.

순서

섹션 제목: “순서”

확인

섹션 제목: “확인”

화면이 app.update.check를 부르면 sidecar가 앱 안에 정해 둔 릴리스 출처에서 서명된 설명(descriptor)을 받아 옵니다. 출처는 빌드에 https 한 곳 이상으로 적혀 있고, 요청마다 그리고 이동(redirect) 응답의 다음 주소마다 요청 전에 허용 목록과 맞춥니다. 사용자 정보, 경로, 쿼리가 든 주소는 출처로 받지 않고, http는 거절합니다.

받은 설명은 이 순서로 걸러집니다.

  1. 서명·서명자·빌드·지문·대상 OS를 모두 확인합니다. 설명 안의 값과 서명된 바이트의 값이 하나라도 다르거나 대상 OS가 이 설치와 다르면 untrusted-release입니다.
  2. 버전 비교. 릴리스 순서(X.Y.Z 또는 X.Y.Z-rc.N)로 이 설치의 버전과 견줍니다. 더 낮은 버전이면 “최신”으로 답하고 내려받기를 권하지 않습니다. 같은 버전이고 빌드도 같으면 “최신”입니다. 같은 버전인데 빌드가 다르면 untrusted-release로 거절합니다. 공개 릴리스 출처에서 테스트 빌드(rc)가 오면 거절합니다.
  3. 새 버전이면 후보로 기억하고 화면에 알립니다.

출처에 닿지 못하거나 시간이 넘으면 check-unavailable입니다. 이것은 “새 버전 없음”과 다른 답입니다. 명시적 확인의 상한은 45초(EXPLICIT_CHECK_LIMIT)입니다. 한 번에 하나만 돕니다.

받기와 검증

섹션 제목: “받기와 검증”

app.update.download가 기억해 둔 후보를 받습니다. 후보가 없으면 update-not-ready입니다.

  1. 서명된 설명을 다시 확인합니다.
  2. 서명된 목록(manifest)에 적힌 크기를 총량으로 삼아 update-progress 사건으로 받은 바이트를 알립니다. 사건은 1초에 네 번까지만 보냅니다.
  3. 다 받은 바이트의 크기와 SHA-256 지문을 목록과 설명에 맞춥니다. 하나라도 다르면 untrusted-release이고 아무것도 놓지 않습니다.
  4. 맞으면 keeper의 현재 바인딩을 먼저 읽고(keeper가 답하지 않으면 거절), 검증된 묶음을 app-release:<platform>:<build id>:<digest> 키로 keeper가 쥔 자리에 놓습니다(stage). 같은 서명 입력을 다시 받으면 같은 키라서 앞서 놓은 것의 영수증이 답으로 옵니다. 답은 artifactRef입니다.

여기까지는 설치된 것을 바꾸지 않습니다. 앱을 닫아도 놓은 묶음은 남습니다.

기다릴지 지금 할지

섹션 제목: “기다릴지 지금 할지”
  • 지금 바로(now). 곧바로 적용으로 갑니다.
  • 일이 끝나면(quiet). update.arm이 멈추는 것 없이 할 수 있는 확인만 하고 update-armed.json에 “기다리는 중” 기록을 씁니다. 그다음 update.await-quiet이 엔진의 update.activity를 2초(WAIT_POLL)마다 읽어, Lyra 화면에서 답하는 대화와 도는 명령이 없어질 때까지 기다립니다. 읽지 못하면 간격을 늘려 30초까지 갑니다. 한 번의 호출은 최대 600초(AWAIT_QUIET_WITHIN)를 기다리고, 숫자가 그대로면 같은 답을 주며 앱이 다시 부릅니다. 기다림 자체에는 시간 한도가 없습니다. 조용해지면 앱이 update.apply를 quiet로 보냅니다. 이때 엔진은 일이 있으면 끊지 않고 busy로 거절하고, 거절되면 다시 기다립니다. 거절 뒤에는 숫자가 조용해 보여도 최소 30초(QUIET_RETRY_AFTER)를 둔 뒤 다시 보냅니다. update.disarm이 기다림을 취소하며, 기다림은 잠금도 예약도 전환 기록도 쥐지 않으므로 취소하면 남는 것이 없습니다.

적용

섹션 제목: “적용”

update.apply는 sidecar의 명시적 적용 입구가 받습니다. 사람이 누른 것만 이 입구를 지나고, 호출자가 묶음이나 모드를 정할 수 없습니다. 전체 한도는 660초이고 내역은 다음과 같습니다.

몫 시간
엔진을 띄우는 일(keeper는 있는데 엔진이 없을 때), 앱 단계 읽기, 일 세기(APPLY_BEFORE_G) 20초
엔진 교체 요청 engine.update(중간에 자르지 않음. 자르면 결과를 모르게 됨) 630초
옮기지 못했을 때 다시 세는 일(APPLY_AFTER_G) 5초
답이 main에 닿는 여유 5초

순서는 이렇습니다.

  1. 이미 다른 업데이트가 도는 중이면 그것을 update.await-running(상한 630초)으로 기다린 뒤 한 번 더 보냅니다.

  2. keeper에 엔진이 없으면 사람이 누른 것을 동의로 보고 사람이 멈춘 기록을 지우고 엔진을 띄웁니다. 20초 안에 뜨지 않으면 update-engine-not-started입니다. 이때 띄우는 엔진은 설치된 버전입니다. 새 버전은 아래의 교체로만 뜹니다.

  3. 도는 명령과 서비스, 터미널을 센 뒤 끝날 수 있는 일이 있으면 “끝났을 수 있음” 기록(app.update.ended-work)을 먼저 씁니다. 기록을 쓰지 못하면 교체를 요청하기 전에 멈춥니다.

  4. engine.update가 keeper의 activation.sock으로 갑니다. keeper의 전환 기록이 아래 단계를 하나씩 지나며 Failed나 Unknown이 아니면 Ready로 끝납니다.

    단계(Phase) 뜻
    Reserved 영수증과 새 일 막기 표시를 먼저 기록
    Quiescing 옛 엔진이 일을 정리
    OldExited 옛 엔진의 종료와 쓰기 잠금 해제를 확인
    Snapshotting → SnapshotReady 읽기 전용 사본을 만들어 목록까지 게시
    Starting 새 세대를 띄움
    Rebinding 새 엔진이 잠금을 쥐고 keeper의 보관 목록을 맞춤
    Ready 마지막 준비 게시가 확정

    Deferred는 옛 엔진이 그대로 있고 다음 확인에서 다시 계획한다는 뜻입니다. sidecar는 이 단계 변화를 2초마다 읽어 update-progress로 알립니다.

  5. 엔진이 새 버전이 된 뒤에야 앱 단계가 이어집니다. 답에 appInstall이 실려 오는 경우는 설치된 앱의 빌드가 묶음의 빌드와 다를 때뿐입니다. keeper가 들어오는 빌드를 받지 않는다고 거절하면, 사람이 두 번째 대화에서 확인한 뒤 update.retire-keeper가 keeper를 거두고 앱 단계로 갑니다. 그 밖의 거절(내리는 버전 막이, 검증 안 된 묶음 등)은 keeper를 거두어도 낫지 않으므로 거두지 않습니다.

앱 바꾸기

섹션 제목: “앱 바꾸기”

main의 넘기기(HandoffCoordinator)가 정해진 순서로 앱을 닫고 새 버전에 맡깁니다.

  1. 입력 확인(input-confirmed): 사람이 저장·버리기·머무르기를 정한 뒤입니다.
  2. sidecar에 입력 끝(sidecar-eof)을 보내고, 끝난 것을 확인합니다(sidecar-exited).
  3. 새 버전의 sidecar 복사본(update/transitions/<uuid>/)을 --update-worker install-app <descriptor> 인자만으로 띄웁니다(worker-launched). 복사본은 검증되어 놓인 묶음에서 옵니다.
  4. 앱을 닫습니다(app-closing).

3번이 실패하면(worker-launch-failed) 앱을 닫지 않고 sidecar를 한 번 다시 띄웁니다(sidecar-restarted).

worker는 옛 앱의 main이 끝날 때까지 30초(PARENT_EXIT_WAIT) 기다립니다. 끝나지 않으면 app-update-app-still-running으로 아무것도 바꾸지 않고 기록만 남기며, 옛 앱이 그 기록을 스스로 읽습니다. 끝났으면 묶음을 다시 검증해 설치된 앱을 바꿉니다. Windows는 들어오는 설치기를 한 번 눈에 보이게 돌립니다. 결과 기록을 먼저 쓰고 앱을 다시 엽니다.

결과 뜻
installed(app-update-installed) 바꿈. 묶음과 놓아 둔 파일을 치웁니다.
not-installed 바꾸지 않았고 옛 앱이 그대로 열립니다. 이유 코드가 따라옵니다(묶음이 맞지 않음 app-update-not-started, 백업 공간 부족 등. 공간 부족은 찾은 바이트와 필요한 바이트가 함께 옵니다).
unknown 설치된 것이 어느 쪽인지 모릅니다. 백업과 체크포인트를 남기고 복구가 이어받습니다.

새로 연 앱이 app.update.result로 결과를 한 번 읽고 app.update.result-ack로 확인하면 그 기록이 지워집니다.

서버의 lyra-daemon 맞추기

섹션 제목: “서버의 lyra-daemon 맞추기”

서버의 lyra-daemon은 앱을 바꾼 것과 따로 맞춥니다. 엔진이 2초마다 연결된 daemon을 살펴(daemon.adoption.status) 앱의 버전과 견줍니다. 판단은 결정만 하는 순수 함수입니다.

상황 결정
그 끝점을 쥔 daemon이 없음 새로 띄움(StartNew)
같은 버전 그대로 씀(Adopt)
링크 프로토콜이 다름 daemon-protocol-mismatch로 거절
앱보다 낮은 버전, 살아 있는 일 0 바로 교체(ReplaceNow)
앱보다 낮은 버전, 일이 있거나 일의 수를 모름 옛 버전을 두고 일이 0이 될 때까지 기다림(AdoptStale)
앱보다 높은 버전 daemon-newer-build-running으로 거절. 내리지 않습니다.
버전을 읽을 수 없음 daemon-product-version-unknown으로 거절

교체는 서버의 lyra-daemon 자신의 확인으로만 합니다. 엔진은 새 일을 닫으라고 하고(close_for_replacement, 10초 안에 끝나야 함) daemon.adoption.replace를 보냅니다. daemon이 자기 버전과 인스턴스, 일의 수를 다시 확인하고 거절할 수 있습니다. 교체가 끝나면 엔진은 옛 연결을 닫고, 옛 daemon이 놓이길 기다린 뒤 다시 붙습니다. 같은 서버에 60초 안에 다시 교체를 보내지 않습니다. 보낸 뒤 전송이 끊겨 결과를 모르면 그 사실을 60초 동안 쥐고, 지나도 새 인스턴스가 확인되지 않으면 문제로 올립니다.

되돌리기

섹션 제목: “되돌리기”

되돌리기는 앱과 엔진을 함께 앞 버전으로 옮깁니다. 화면은 engine.rollback-plan으로 계획을 받아 사람이 확인한 뒤 engine.rollback을 보냅니다. 앱 쪽은 main이 --update-worker rollback으로 같은 넘기기 길을 돕니다. 이 worker는 받은 서술자에 의존하지 않고, 설치가 스스로 기록해 둔 앞 앱을 확인해(로컬 상대 증명) 그 앱으로 복원합니다. 복원 결과를 먼저 기록하고 앱을 다시 엽니다. 결과를 모르면 앱을 다시 열지 않고 원래 전환을 남깁니다.

단계마다 실패하면

섹션 제목: “단계마다 실패하면”
단계 실패 결과
확인 출처에 못 닿음, 45초 초과 check-unavailable. 후보 없음.
확인 서명·빌드·지문·OS 불일치, 같은 버전 다른 빌드 untrusted-release
받기 후보가 없음 update-not-ready
받기 크기나 지문이 다름 untrusted-release. 묶음을 놓지 않음.
받기 keeper가 답하지 않음 거절. 옛 바인딩으로 놓지 않음.
적용 다른 업데이트가 도는 중 busy. update.await-running으로 기다림.
적용 엔진이 20초 안에 안 뜸 update-engine-not-started
적용 quiet인데 일이 있음 busy. 다시 기다림.
적용 Failed 옛 버전이 그대로 있고 원래 영수증을 보존. 이유 코드가 따라옴.
적용 Unknown, 또는 전환이 끝나지 않은 채 앱이 다시 열림 새 쓰기 주체를 허가하지 않음. 이후 엔진 시작도 멈추고(engine-update-state-unknown, engine-recovery-required), lyra update recover --engine app --transition latest --resolution restore-recorded를 안내함.
앱 바꾸기 worker를 못 띄움 앱을 닫지 않고 sidecar를 한 번 다시 띄움

앱 바꾸기 결과 기록을 쓰지 못함 app-update-result-unwritable을 앱 로그에 남기고 앱은 다시 엶

서버의 lyra-daemon 교체 요청 뒤 전송이 끊김 결과를 모르는 것으로 60초 보관

다시 시작해도 남는 것

섹션 제목: “다시 시작해도 남는 것”
  • 받아 놓은 묶음: keeper가 쥐고 있어 앱이나 엔진이 다시 떠도 남습니다. 같은 서명 입력으로 다시 받으면 같은 키라서 앞의 영수증으로 이어집니다.
  • 전환 기록과 영수증: 단계마다 먼저 기록하므로 중간에 끊겨도 남습니다. 끝나지 않은 전환이 있으면 앱이 새로 시작하는 엔진도 그것을 먼저 읽습니다(Engine start and restart).
  • “기다리는 중” 기록: update-armed.json에 있어 앱을 다시 열면 update.armed로 읽습니다.
  • 앱 바꾸기의 결과 기록: 새 앱이 읽고 확인하기 전까지 남습니다.
  • “끝났을 수 있음” 기록: 옮기지 않은 업데이트가 일을 끝내지 않았음을 확인하기 전에는 남습니다. 지우지 못하면 “아무것도 안 끝남”이 아니라 “끝났을 수 있음”으로 둡니다.
  • 서버의 lyra-daemon의 교체 상태: 엔진의 메모리에만 있습니다. 엔진이 다시 뜨면 처음부터 살핍니다.
