Credentials

This content is not available in your language yet.

Lyra는 오래 남는 비밀을 OS 자격 증명 저장소에 둡니다. macOS는 Keychain, Windows는 Credential Manager입니다. 예외는 아래 저장소 밖에 모았습니다. 이 페이지에는 비밀 값을 적지 않고, 이름과 모양만 적습니다.

저장소에 두는 것

섹션 제목: “저장소에 두는 것”

저장소를 부르는 길은 하나입니다. lyra-credential-vault crate가 keyring crate(=4.2.0으로 못 박혀 있습니다)의 Entry를 서비스 이름과 계정 이름으로 열고, 쓰기는 set_secret, 읽기는 get_secret, 지우기는 delete_credential을 부릅니다. 이 길은 macOS와 Windows에서만 컴파일됩니다. 한 호출의 오류는 저장소에 없음(NoEntry)이면 Missing, 접근 거부(NoStorageAccess)이면 Denied, 그 밖의 플랫폼 오류와 모호함은 InconsistentStorage로 바뀝니다.

서비스 이름은 둘입니다.

서비스 계정 담는 것 쓰고 읽는 쪽
lyra <이름공간>-credential-<번호> 금고 목록에 오른 자격 증명의 비밀(SSH 자격 증명, 모델 엔드포인트 키) 엔진이 쓰고 읽고 지웁니다. 모델 엔드포인트 키는 호스트 daemon이 읽기만 합니다.
lyra-app-secret <이름공간>-connection-<id> Jira · GitHub 연결의 비밀번호나 토큰 엔진이 연결을 추가할 때 쓰고, 읽고, 연결을 지울 때 지웁니다.
lyra-app-secret <이름공간>-company-id-password-<해시> 회사 게이트웨이의 ID 비밀번호 엔진의 비밀번호 실행기가 씁니다. 금고 목록에도 금고 문서에도 기록이 없습니다. 서버를 지울 때는 그 서버가 로그인한 계정의 값을 저장소와 엔진 메모리에서 함께 지웁니다. 같은 계정을 쓰는 다른 서버가 있어도 지우고, 그 서버는 다음 연결 때 다시 묻습니다. 별칭으로 추가한 서버는 지울 때 ssh -G를 한 번 돌려 계정을 찾고, 돌리지 못해도 삭제는 그대로 되며 값은 저장소에 남습니다.
lyra-app-secret <이름공간>-update-github-token 옛 업데이트 토큰 지우기만 합니다. 내용은 읽지 않습니다.
  • <이름공간>은 엔진에서는 lyra-app-<설치 번호>입니다. 설치 번호는 엔진 폴더의 install/id.json에 한 번 만든 16자리 16진수입니다. OS 저장소는 사용자 하나에 하나라서, 번호를 설치마다 1부터 세면 다른 설치본이 남긴 항목과 계정 이름이 겹치기 때문입니다. 호스트 daemon은 설치 번호 없이 이름공간 lyra-daemon을 씁니다.
  • <번호>는 이름공간 안에서 1부터 세는 번호이고, 앱 비밀 이름(<이름>)은 소문자, 숫자, -만 받습니다.
  • 회사 비밀번호의 <해시>는 게이트웨이 호스트 · 포트 · 도메인 · 사원 ID를 JSON 배열로 묶은 것의 SHA-256입니다. 저장소 항목 이름에 호스트나 사원 ID가 드러나지 않게 하려는 것입니다.
  • 목록에 오른 자격 증명은 비밀 값이 없는 메타데이터가 엔진 폴더의 credential-vault.json에 따로 남습니다(Folders). 앱 비밀은 목록에 오르지 않습니다.

사람이 lyra credential로 넣을 수 있는 것은 SSH 자격 증명(add-ssh)이고, 방법은 agent(비밀 없음), key, key-with-passphrase입니다. --method password는 명령줄이 password-needed로 거절합니다. 모델 엔드포인트 키를 넣는 연산(credential.add-model-endpoint)은 profile.endpoint-removed로 거절하고 저장소를 건드리지 않습니다. 그래도 호스트 daemon에는 그 키를 읽어 에이전트 자식의 환경에 한 번만 넣는 코드가 남아 있습니다(구현 현황에 적어 둡니다).

다른 프로그램의 항목을 읽는 곳

섹션 제목: “다른 프로그램의 항목을 읽는 곳”

앱의 HTTP 피드(app_http)는 에이전트가 macOS Keychain에 둔 로그인 항목을 읽기만 합니다. 서비스 이름은 Claude Code-credentials이거나 그 뒤에 작업 폴더 경로의 SHA-256 앞 8자리 16진수가 붙은 꼴이고, 계정은 사용자 이름이거나 claude-code-user입니다. 읽는 방법은 /usr/bin/security find-generic-password -s <서비스> -a <계정> -w 한 번이고, 환경을 비우고 표준 입출력을 막고 5초 예산 안에서 합니다. 항목이 없을 때(종료 코드 44)만 “없음”이고 다른 오류는 거절합니다. 이 항목에 쓰거나 지우지 않습니다. macOS가 아니면 이 읽기는 지원하지 않습니다.

저장소 밖에 두는 것

섹션 제목: “저장소 밖에 두는 것”
무엇 어디에 까닭
SSH 비밀번호 엔진 프로세스의 메모리뿐 저장소 규칙의 예외입니다. 렌더러 · preload · main · sidecar · CLI의 입력 버퍼는 넘긴 뒤 지우고 어디에도 쓰지 않습니다. 금고는 메모리 비밀번호 방식이 켜지면 비밀번호 방법의 저장을 InvalidCredentialInput으로 거절합니다.
회사 게이트웨이의 일회용 코드(OTP) 저장하지 않음 기억하지 않습니다.
사람의 표준 SSH 키 사람의 SSH 폴더(~/.ssh, Windows는 %USERPROFILE%\.ssh) Lyra는 그 키를 소유자 전용 확인을 통과할 때만, 메모리로만 읽습니다. 자기 파일 · 로그 · SQLite · OS 저장소에 복사하지 않습니다.
엔진 손님 통로 토큰 엔진 폴더의 home-runtime.json 엔진이 뜰 때마다 새로 만드는 값이라 오래 남는 비밀이 아닙니다. 파일은 사용자 전용이고 손님은 권한을 먼저 확인합니다. 토큰 형식은 Debug로 내지 않고 버릴 때 지웁니다.
에이전트 자식의 환경에 넣는 엔드포인트 키 자식의 환경 변수 한 칸 스폰 순간에 저장소에서 읽어 넣고 준비된 상태에는 남기지 않습니다.
Linux의 모든 영속 비밀 ~/.lyra/credentials/credentials.json 보안 점검(v1 공개 전)까지의 임시 예외입니다. 파일은 0600, 그 폴더는 0700이고 값은 평문입니다.

Linux 파일은 이렇게 다룹니다. 읽을 때마다 링크를 따라가지 않고 열어 그 손잡이가 일반 파일이고, 유효 사용자가 주인이며, 그룹과 다른 사람의 권한 비트가 없는지 확인합니다. 아니면 경로와 찾은 값과 고치는 명령을 담은 문장으로 거절하고, 권한을 스스로 고치지 않으며, 값을 읽지도 않습니다. 쓸 때는 폴더의 잠금을 쥐고 전체 문서를 같은 폴더의 임시 파일(0600)에 써서 동기화하고 이름을 바꾸고 폴더를 동기화합니다. 이름 바꾸기 전에 끊기면 옛 파일이 온전히 남고 임시 파일이 하나까지 남을 수 있으며, 다음에 열 때 같은 잠금 아래에서 지웁니다. ~/.lyra는 계정 소유여야 하지만 그룹 쓰기가 가능해도 되고(umask 002 계정), 경계는 credentials/ 폴더입니다. 서버 Linux는 호스트 daemon용 OS 저장소가 없어서, 묶인 엔드포인트 키를 준비 단계에서 session-endpoint-key-store-unavailable로 거절합니다.

이 두 예외는 다른 개인 키, 키 암호, 모델 토큰, 앱 비밀을 포함하지 않습니다. 그래서 위 표의 앱 비밀(연결 토큰, 회사 비밀번호)은 모두 OS 저장소에 있습니다. 서버에 있는 다른 자격 증명의 보관 방법은 이 규칙이 정하지 않습니다.

Windows와 Credential Manager

섹션 제목: “Windows와 Credential Manager”

Windows의 읽기와 쓰기도 keyring을 거칩니다. 제품 코드가 Windows 자격 증명 API를 직접 부르는 곳은 하나입니다. 저장소가 서 있는지만 묻는 CredEnumerateW이고, 일부러 아무것도 맞지 않는 거르개(lyra-secret-store-probe-*)로 물어서 비밀 값을 읽지 않습니다. CredReadW · CredWriteW · CredDeleteW를 직접 부르는 코드는 시험 도구에만 있습니다.
