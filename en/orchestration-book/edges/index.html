Edge cases

Uncommon situations that can be confusing. Filter by area, or look one up by a word.

Depth and roles

Section titled “Depth and roles”

A Worker tries to bypass the depth limit with lyra session open and lyra session prompt

Section titled “A Worker tries to bypass the depth limit with lyra session open and lyra session prompt”

An agent’s lyra session open and lyra session continue follow the same rules as starting a new Orchestrator. Workers are refused. session prompt is limited to the caller’s tree or sessions it started.

A handoff returns to its giver (A → B → A)

Section titled “A handoff returns to its giver (A → B → A)”

Handoff adds no parent edge. A running task cannot be handed to a receiver inside its executing Worker’s branch: that would create a cycle.

Hand off to a deeper session in another tree

Section titled “Hand off to a deeper session in another tree”

The receiver becomes owner in place. The executing Worker and its branch move beneath it; the entire branch must fit within the depth limit.

A looping chain reaches the 8-step read cap

Section titled “A looping chain reaches the 8-step read cap”

Stop reading at 8 steps and treat it as exceeding the limit. This is why the maximum setting is 7.

A move would exceed the limit

Section titled “A move would exceed the limit”

Recheck the entire branch. If any session goes over the limit, the entire move is refused.

Demote a Lead with children to Worker

Section titled “Demote a Lead with children to Worker”

Allowed only without live children. Otherwise it is refused and you are told to finish or move the children first.

A Lead-started new Orchestrator tries to start a Lead

Section titled “A Lead-started new Orchestrator tries to start a Lead”

The new Orchestrator stands at that Lead’s depth (1). With limit 2, its child would have depth 2, which is not a Lead position, so the start is refused.

Start a Lead with limit 1

Section titled “Start a Lead with limit 1”

No position for a Lead fits (depth ≤ 0), so it is refused. The Orchestrator can start Workers only.

A Worker tries to start with --role lead

Section titled “A Worker tries to start with --role lead”

A Worker cannot start anything, so it is refused whatever role is requested.

Delivery

Section titled “Delivery”

A brief exceeds 16 KiB

Section titled “A brief exceeds 16 KiB”

The plan accepts up to 256 KiB, but terminal input above 16 KiB is refused. Keep a long brief in a file and have the agent say its path.

Multiline input to an agent that has never shown bracketed paste

Section titled “Multiline input to an agent that has never shown bracketed paste”

Refused when safe multiline input cannot be verified. This is why the footer is one line.

Claude Code changes its paste wrapper again

Section titled “Claude Code changes its paste wrapper again”

If the wrapper cannot be strictly removed, the binding stays unknown (a yellow ?). A match is never guessed.

A person is typing in the Worker’s window

Section titled “A person is typing in the Worker’s window”

Text already in the box holds a task until it is cleared, and can end in the not-ready refusal. After that wait, Lyra types anyway, and its text can mix with what the person is typing. A message notice and a recovery continue do not wait for the box, so their Enter can send what the person left there.

An agent whose input field cannot be read

Section titled “An agent whose input field cannot be read”

Text is sent without waiting for an empty input. Known dialogs still cause refusal.

The notice line’s outcome is unknown

Section titled “The notice line’s outcome is unknown”

It is not entered again in the same execution: completion of the old input is unproven, and only a different confirmed execution clears it. The sender’s wait wakes with message-held. Do not resend; check message show and session show, and ask the person if it stays uncertain.

Message a closed session

Section titled “Message a closed session”

A send to a closed or failed session is refused unless its address was adopted. After adoption, ordinary new mail follows the adopter. Otherwise, choose an open session.

Supervision

Section titled “Supervision”

An agent whose status Lyra cannot read

Section titled “An agent whose status Lyra cannot read”

There is no status to bind a turn to the task, so progress is absent and task wait does not emit worker-stopped. Without evidence, Suspect appears at 10 minutes and a stall notice at 60 minutes.

Esc closes an approval dialog without Stop

Section titled “Esc closes an approval dialog without Stop”

A person must answer approvals. If waiting persists after the dialog closes, inspect the actual session and notify the owner.

A Lead waits inside a foreground task wait

Section titled “A Lead waits inside a foreground task wait”

A task wait running in the foreground is a tool execution. After the tool-run limit, a wait notification can tell the parent once, but the Lead is not stopped, retried or escalated. If the turn ends while child work continues, it is Waiting{Workers}, which is not a stall either.

A login error

Section titled “A login error”

A person’s decision is needed, so Lyra notifies at once instead of typing continue. Permissions, invalid requests, model refusals and quota failures behave the same way.

The process ends

Section titled “The process ends”

The provider session is continued only after termination is confirmed. If it cannot be confirmed, Lyra notifies.

Handoff and adoption

Section titled “Handoff and adoption”

Take over after an Orchestrator disappears

Section titled “Take over after an Orchestrator disappears”

A new session uses task adopt --from. Evidence that the old owner ended is required, and the ownership generation increases, so requests from the old owner are refused. The depths of the Workers do not change.

The receiver does not read within 60 seconds

Section titled “The receiver does not read within 60 seconds”

A never-claimed handoff returns ownership to the giver if the wait expires, the recipient closes or the task attempt ends. A claimed delivery without a confirmed ack has an unknown outcome and keeps ownership unchanged until it is explicitly resolved.

worker start --handoff for a task that runs only while connected

Section titled “worker start --handoff for a task that runs only while connected”

Refused: a task handed to another owner must not depend on the connection.

Connection and unknown

Section titled “Connection and unknown”

An outdated lyra-daemon on the remote computer

Section titled “An outdated lyra-daemon on the remote computer”

lyra-daemon on this computer enforces depth, roles and supervision times. Task delivery and turn binding need support from lyra-daemon on the session’s computer. Without binding evidence, the result stays unknown.

An agent calls --abandon-unproven

Section titled “An agent calls --abandon-unproven”

Refused, because only a person can abandon a task without termination evidence. The agent is told to ask the person.

A quarantined Worker terminal

Section titled “A quarantined Worker terminal”

Reuse and release are refused, and so is dispatch into that session. A person closing the session is the way out.

Report

Section titled “Report”

A late report arrives after a retry

Section titled “A late report arrives after a retry”

A report from an old attempt is explicitly refused as StaleAttempt, not blurred into “not applied”.

The same Worker reports twice

Section titled “The same Worker reports twice”

Only the first accepted report sends a notification.

The attempt limit is reached (Planned)

Section titled “The attempt limit is reached (Planned)”

Dispatch or retry is refused at the attempt limit. Check the limit applied to this task.

Settings

Section titled “Settings”

Lower the depth limit while deeper sessions run

Section titled “Lower the depth limit while deeper sessions run”

Running sessions are left alone. Only new starts are refused under the new limit. Settings shows a warning such as “There are K running sessions at depth N.”

The saved depth is invalid (not a number, 0, or 8+)

Section titled “The saved depth is invalid (not a number, 0, or 8+)”

It falls back to the default 2. A corrupt value must not become a way to remove the limit.

An agent tries to raise its own depth limit

Section titled “An agent tries to raise its own depth limit”

Refused. The Settings action is registered so that only the screen (renderer) can call it, and there is no CLI write verb. lyra-daemon on this computer also rejects writes that carry an agent’s call context. The refusal text says to ask the person to change Settings.

“Is it a person?” is not a security boundary

Section titled ““Is it a person?” is not a security boundary”

A call without LYRA_SESSION_ID is treated as a person. If an agent removes that variable and calls the CLI, it looks like a person. That is why Settings has no CLI write at all.

No updates time ≥ stall notification time

Section titled “No updates time ≥ stall notification time”

Refused when the setting is outside the allowed range. Zero and values of 7 days or more are also refused. The screen prevents invalid choices, and a refused write shows as red text under the row.

Two windows change settings at once

Section titled “Two windows change settings at once”

Revisions are compared, and a write based on outdated settings is refused. The screen reloads and shows the current values.

A supervision time was changed but nothing changed

Section titled “A supervision time was changed but nothing changed”

Saving is immediate, but the values apply when lyra-daemon on this computer restarts (restartRequired). The screen shows “↻ Restart to apply”.

The concurrent Worker cap is reached (when enabled)

Section titled “The concurrent Worker cap is reached (when enabled)”

A new Worker is refused, and the running count and limit are shown. The cap is off by default.
