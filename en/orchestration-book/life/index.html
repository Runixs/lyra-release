The life of a task

This page follows one task from creation to its report. The four lanes are the Orchestrator, lyra-daemon on this computer, lyra-daemon on the session’s computer, and the Worker terminal. Each step below shows what actually happens and the values involved.

1. Create a task

Section titled “1. Create a task”

0:00 · With --spec-file, the Orchestrator calls lyra worker start to create a task and make the caller its owner. Use --task for an existing ready task instead. A one-line reporting footer is appended to the brief.

  • Brief limit: 256 KiB (in the plan)
  • Reporting footer: same line for a one-line brief; otherwise the final paragraph

2. Check depth

Section titled “2. Check depth”

0:00 · lyra-daemon on this computer measures depth through recorded parents and starters. It enforces the role, depth limit, default role and permitted Orchestrator starters. Workers cannot start sessions. Agent-started Orchestrators and Leads need room for their own children under the 8-step read cap.

  • Depth limit: 1–7; default 2
  • Read cap: 8 steps; cycles and overflow are refused
  • Lead position: depth ≤ limit − 1

3. Dispatch — send to lyra-daemon

Section titled “3. Dispatch — send to lyra-daemon”

0:01 · lyra-daemon on this computer asks lyra-daemon on the session’s computer to enter the text, using the connection for remote servers. Each task has a disconnect policy; by default it keeps running when the connection drops.

  • Total budget: 80 s = 60 s input readiness + 20 s writing
  • Default disconnect policy: keep running when disconnected

4. Wait for empty input

Section titled “4. Wait for empty input”

0:01 · lyra-daemon waits until the Worker’s input stays empty for 1.5 seconds. If it is still not ready after 60 seconds, input is refused. A known dialog also prevents input. Text a person left in that box counts as not empty, so it can end in that refusal; keys pressed after the wait has passed do not stop Lyra. Agents whose input cannot be read are sent text without this wait.

  • READY_WAIT: 60 s
  • READY_HOLD: 1.5 s

5. Request line and paste

Section titled “5. Request line and paste”

0:03 · A Claude Code Worker receives a request line before the pasted brief. Input is limited to 16 KiB; NUL and control characters are refused. Multiline input requires observed bracketed-paste support in that terminal.

  • Input limit: 16 KiB
  • Multiline requirement: refuse unless multiline paste support is verified

6. Send Enter separately

Section titled “6. Send Enter separately”

0:03 · After writing the text, lyra-daemon waits briefly and sends Enter separately. Codex gets one more Enter if no turn signal arrives within 1.2 seconds. It then watches for 8 seconds to determine whether the turn started, is awaiting permission, or did not start.

  • Wait: 50 ms + 1 ms per 4096 bytes (per 64 bytes on Windows)
  • CODEX_RESUBMIT: 1.2 s
  • TURN_WAIT: 8 s
  • One write: 20 s

7. lyra-daemon binds a turn to the task

Section titled “7. lyra-daemon binds a turn to the task”

0:04 · lyra-daemon stamps the task on the status of a terminal Worker from its own record of the task it typed. No agent hook is involved, and a turn it cannot match stays unknown; the match is never guessed.

  • Status source: OSC 7501 · screen rules · process exit
  • Prompt source: lyra-daemon’s record of the typed task
  • Agent hooks: none

8. Progress signal

Section titled “8. Progress signal”

0:05 · The agent’s status reports and its screen travel through lyra-daemon on the session’s computer to lyra-daemon on this computer, which checks supervision every 2 seconds. Only evidence counts as progress. While the status is Working, new output on the screen counts as progress. A live process is not progress. Human approval and tool execution are legitimate waits. Past a limit (by default 10 and 60 minutes), Lyra only marks a long wait and sends a wait notification; it does not stop, retry or escalate. The settings apply after lyra-daemon on this computer restarts.

  • Supervision interval: 2 s
  • Wait reasons: AwaitingHuman · LongTool · NativeRetry

9. If quiet (a branch)

Section titled “9. If quiet (a branch)”

+10 / +60 min · By default, 10 minutes without progress yields Suspect: the board shows No updates and task wait returns worker-suspect. At 60 minutes, lyra-supervisor sends the owner one notification. A person or Orchestrator decides the next action. Change both times in Orchestration settings; they apply the next time lyra-daemon on this computer starts.

  • Suspect: 10 min
  • Stall notification: 60 min
  • Storage: home_supervision_settings
  • Operation: supervision.settings.show / set

10. Report

Section titled “10. Report”

12:40 · The Worker calls lyra task report as instructed by the footer. The first accepted report completes the task and records a notification in the same transaction. A late report from a prior attempt is explicitly refused as StaleAttempt.

  • Outcome: completed · failed · stopped
  • Notification: first report only

11. Report notification

Section titled “11. Report notification”

12:40 · lyra-daemon on this computer posts a notification to the task owner’s mailbox. The summary is truncated to 320 characters and wrapped in JSON. lyra-daemon on the session’s computer delivers only a notice line, typed at the agent’s ready prompt: an agent in the middle of a turn gets it after that turn ends. A refused line is retried after 10 seconds.

  • Summary limit: 320 characters
  • Notice line: You have 1 Lyra message. Run lyra message check.
  • Retry: after 10 s

12. task wait wakes

Section titled “12. task wait wakes”

12:41 · lyra task wait checks message.check in 30-second slices. lyra-daemon on this computer holds a call for up to 60 seconds, checking every 250 ms. A result exits with 0. Message batches replay until explicitly acknowledged. If there are no tasks or messages, the second empty check returns idle.

  • One slice: 30 s (SLICE_MS)
  • Limit of lyra-daemon on this computer: 60 s (MAX_WAIT)
  • Check interval: 250 ms
