Handoff

Ownership of one task changes. It is not the same as a message. Below, the four actions are compared in the same tree.

The short answer

Section titled “The short answer”

Handoff travels as a message. When the recipient reads and acknowledges it, the entire task becomes theirs. Results, questions, cancellation and retries then belong to the receiver; the giver lets go.

  • Only one task transfers. The giver’s other tasks and Workers, and the receiver’s existing tasks, stay as they are. For a running task, only its executing Worker and branch follow.
  • Only hand off a task you own. The task you are executing belongs to the parent that assigned it, so you cannot hand it off. A Worker asks its parent.
  • lyra message send sends text only. It changes neither ownership nor parents nor who receives results.

The receiver becomes the new parent

Section titled “The receiver becomes the new parent”
  • An existing receiver stays in place. The executing Worker and its branch move beneath it. For an unstarted task, the receiver does the work directly.
  • Handoff to the executing Worker itself, or to a new session with worker start --handoff, takes the giver’s position: same parent, depth and role.
  • Only the receiver gets the results. Handoff, moving, adoption and messaging are separate actions.

Depth: refuse if any session in the moving branch exceeds the limit

Cycle: refuse a receiver inside the moving Worker’s branch

Role: a Worker cannot receive children — pick another receiver (changing a role is planned)

Handoff, message, move, adopt

Section titled “Handoff, message, move, adopt”

Handoff

Section titled “Handoff”

task handoff

Transfer one task through a message. The receiver handles other messages in the batch, explicitly acknowledges it, verifies ownership, then executes the task it was handed. The receiver stays in place; a running Worker and its branch move beneath it. Only the receiver gets results.

Transfer a work item with its assignee

Try it in the same tree:

Sessions in the picture: Orchestrator, Lead 1, Lead 2, Worker

  1. 0:00 A Worker executes task T assigned by Lead 1. Lead 1 owns T.
  2. 0:10 Lead 1 hands task T to Lead 2. Lead 2 becomes owner only after explicitly acknowledging the handoff delivery.
  3. 0:12 Lead 2 prints the batch with message check, then runs message ack. It becomes owner of T. The Worker and its branch move beneath Lead 2, which stays at depth 1; the moved Worker is at depth 2.
  4. 9:00 The Worker reports. Lead 2, the owner, receives the notification. Lead 1 does not.
  5. — A new session or the executing Worker itself takes the position of Lead 1, the giver. The handoff is refused if the branch exceeds the limit, the receiver is inside that branch, or the receiver is a Worker that would gain a child.

Message

Section titled “Message”

message send

Transfers nothing. Only text travels. An idle agent receives a notice line and decides what to do with the message.

A note

Try it in the same tree:

Sessions in the picture: Orchestrator, Lead 1, other session

  1. 0:00 Lead 1 asks another session “Can you do T?” as an urgent message (lyra message send --urgent). A non-urgent message is held up to the set interval (5 minutes by default) and delivered together with others.
  2. 0:01 lyra-daemon on this computer enters one notice line, not the message body.
  3. 0:05 The receiver reads and decides for itself. Ownership and position stay unchanged. T is still Lead 1’s task.
  4. — To do the work, the receiver must make it its own task. Results do not automatically return to Lead 1.

Move

Section titled “Move”

session move

Move a session and its branch beneath another parent. Reports from its task go to the new parent. A person, the tree’s Orchestrator, or a Lead above both places initiates it.

Transfer a team

Try it in the same tree:

Sessions in the picture: Orchestrator, Lead 1, Lead 2, Worker

  1. 0:00 The Worker executes T for Lead 1. Lead 1 owns T.
  2. 5:00 A person (or the Orchestrator) moves the Worker beneath Lead 2. The entire branch’s depth is checked again.
  3. 5:01 Lead 2 becomes the Worker’s parent and receives T’s reports. The Worker continues the same work.
  4. — Handoff starts with the task: its owner transfers it and the executing Worker follows. Moving starts with the session: reports follow its new parent. A person, the tree’s Orchestrator, or a Lead above both places moves it.

Adopt

Section titled “Adopt”

task adopt

Take over an ended Orchestrator’s plan, tasks and ordinary unread or claimed mail. Later sends to its old address follow the adopter. Evidence that it ended is required. Working sessions stay as they are.

Take over all work from someone who left

Try it in the same tree:

Sessions in the picture: old Orchestrator, new Orchestrator, Worker, Worker

  1. 0:00 The Orchestrator ended. No one can manage its tasks.
  2. 0:30 A new session calls lyra task adopt --from <old-session>. lyra-daemon on this computer checks evidence that the old session ended.
  3. 0:31 The old session’s plan and every task transfer together to the new session. Pending handoffs are resolved, or remain with an already acknowledged receiver. Worker depths stay unchanged.
  4. — Handoff gives one task from an open owner. Adoption takes everything from an ended owner.

Who may call it; what remains

Section titled “Who may call it; what remains”
  • The current owner calls with the current ownership generation. It is refused if the generation differs or the caller is not the owner. lyra-daemon on this computer verifies the calling session.
  • It is refused if another ownership transfer is already pending.
  • A retained receiver Worker terminal must pass fencing and reuse rules. Lyra reserves it until receipt and releases it if receipt fails. The giver’s terminal stays as it is.
  • The giver’s task wait stops tracking the transferred task. With no tasks left it returns idle. A reporter that is also the owner does not receive a separate report notification.

The 60-second receipt flow

Section titled “The 60-second receipt flow”
  1. requested Accepted lyra-daemon on this computer enqueues the message; owner unchanged
  2. delivering Claimed receiver claims the message; not yet acknowledged
  3. delivered Received message check prints and acknowledges → owner = receiver, generation +1

Receipt requires the receiving agent to print with message check and explicitly acknowledge with message ack. Storing, claiming or printing alone is insufficient. An unknown outcome keeps ownership unchanged until a late acknowledgment arrives. Proven receiver closure lets the original owner resolve it with task handoff --abandon.

Outcome Situation What happens
timeout Not claimed within 60 s Returned
Recipient missing The recipient is absent Returned
Recipient closed The recipient is closed Returned
Task attempt ended Attempt ends before receipt (for example, a report) Not transferred
unknown Claimed but unacknowledged; closes or times out Owner unchanged. A late receipt transfers it then. Proven closure lets the original owner abandon.

Situation table

Section titled “Situation table”

An Orchestrator hands an unstarted task to a new session (worker start --handoff)

Section titled “An Orchestrator hands an unstarted task to a new session (worker start --handoff)”

The receiver takes the giver’s position: a new Orchestrator at depth 0, without a parent, owning and executing the task.

A Lead hands a task it created to a new session

Section titled “A Lead hands a task it created to a new session”

The receiver takes the giver’s position at depth 1 as a Lead and may divide the work.

A Worker tries to hand off the task it executes

Section titled “A Worker tries to hand off the task it executes”

A Worker does not own that assigned task. It asks its parent, which hands it off or reassigns it.

Hand a running task to its executing Worker

Section titled “Hand a running task to its executing Worker”

The Worker and its branch take the giver’s position and role.

Hand a running task to another session (Lead · Orchestrator)

Section titled “Hand a running task to another session (Lead · Orchestrator)”

The receiver stays in place and becomes owner. The executing Worker and its branch move beneath it. Notifications go to the receiver.

Hand a running task to another Worker

Section titled “Hand a running task to another Worker”

Refused: a Worker cannot receive children. Hand it to a Lead or an Orchestrator; changing a role is planned.

Hand a running task to a session inside the executing branch (a Lead’s task to that Lead’s child)

Section titled “Hand a running task to a session inside the executing branch (a Lead’s task to that Lead’s child)”

Refused: cycle (the receiver is inside the moving branch).

Hand the task of a Lead that has children to a deep session

Section titled “Hand the task of a Lead that has children to a deep session”

The entire moving branch is rechecked. If any session exceeds the limit, it is refused, and the depth and limit are shown.

Hand an unstarted task to a sibling (idle)

Section titled “Hand an unstarted task to a sibling (idle)”

The receiver owns and executes it in place. No parent edge is added, so depth does not increase.

Hand an unstarted task to your own parent or ancestor

Section titled “Hand an unstarted task to your own parent or ancestor”

The receiver owns and executes it in place. No cycle is created.

Hand an unstarted task to your own child (idle)

Section titled “Hand an unstarted task to your own child (idle)”

The receiver owns and executes it in place. An existing session keeps its role.

Hand an unstarted task to a sibling’s child or a deeper session

Section titled “Hand an unstarted task to a sibling’s child or a deeper session”

The receiver owns and executes it in place.

Hand an unstarted task to a session in another tree

Section titled “Hand an unstarted task to a session in another tree”

The receiver owns and executes it in place. The task belongs to its tree and the receiver gets the results.

Hand to the Orchestrator at the top of another tree

Section titled “Hand to the Orchestrator at the top of another tree”

The receiver owns it in place at the top. A running Worker moves beneath it.

A session outside a tree (including one opened by a person)

Section titled “A session outside a tree (including one opened by a person)”

An existing session stays where it is. It prints the batch with message check and explicitly acknowledges it with message ack.

The recipient is closed or absent

Section titled “The recipient is closed or absent”

A missing recipient is refused. Closure before any claim returns the task. A claimed delivery without a confirmed ack keeps ownership unchanged until it is acknowledged or explicitly abandoned.

The receiver is remote and disconnected

Section titled “The receiver is remote and disconnected”

It is refused if the target is already disconnected, because the target cannot be reached. A later disconnect returns the task after 60 seconds, unless the message was read, in which case the outcome stays unknown. Tasks that run only while connected cannot be handed off.

The receiver is busy with another attempt

Section titled “The receiver is busy with another attempt”

A ready task transfer is refused if the Worker is already executing another task.

The receiver already has tasks and children

Section titled “The receiver already has tasks and children”

Existing work stays unchanged. It gains one more task and, for a running task, one more child.

The receiver needs to divide the task

Section titled “The receiver needs to divide the task”

New sessions and the executing Worker inherit the giver’s role. Existing receivers keep their role; give a task that must be split to a Lead or an Orchestrator (changing a role is planned).

Return a task A → B → A

Section titled “Return a task A → B → A”

Handoff adds no parent edge, so it creates no cycle.

Who hears results after handoff?

Section titled “Who hears results after handoff?”

Only the receiver, the task owner. The giver does not.

A report races with handoff

Section titled “A report races with handoff”

If the task attempt ends before receipt, ownership is not transferred.

A handoff is already in progress

Section titled “A handoff is already in progress”

Refused, because another ownership transfer is pending.

The old owner cancels or retries after handoff

Section titled “The old owner cancels or retries after handoff”

The former owner’s request is refused because the ownership generation differs.

The giver’s other tasks and children

Section titled “The giver’s other tasks and children”

Only the Worker executing the task being transferred follows it. Other children stay where they are (moving is planned).

The giver’s and receiver’s retained terminals

Section titled “The giver’s and receiver’s retained terminals”

The receiver’s retained Worker terminal is reused after fencing checks, and reserved until receipt. The giver’s terminal stays unchanged.
