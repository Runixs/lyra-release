Scenarios

Status words match the app’s screen: Working, Waiting, Idle, Done.

Basic flow

Section titled “Basic flow”

Two Workers report

Section titled “Two Workers report”

In the app, these scenes were played one step at a time with a picture. This page lists the same steps in order. The bold text is the scene’s time, and “Sessions in the picture” names the boxes in that picture.

Sessions in the picture: Orchestrator, Worker A, Worker B

  1. 0:00 The Orchestrator calls worker start twice. Both Workers have depth 1.
  2. 0:01 The Orchestrator waits with lyra task wait. Its terminal stays quiet inside that command.
  3. 8:12 A reports. lyra-daemon on this computer completes task A and posts a notification; task wait wakes with message.
  4. 8:13 The Orchestrator handles the result, explicitly acknowledges its delivery, then runs task wait again.
  5. 11:40 B reports. Its notification follows the same route.
  6. 11:41 With no tasks or messages left, the second empty check of task wait returns idle.

Message delivery — idle and closed sessions

Section titled “Message delivery — idle and closed sessions”

Sessions in the picture: Orchestrator, Worker A, Worker B

  1. 0:00 The Orchestrator sends idle Worker A an urgent message (--urgent). A non-urgent message is held up to the set interval (5 minutes by default) and delivered together with others.
  2. 0:01 lyra-daemon on this computer coalesces notices per receiver, and lyra-daemon on the session’s computer delivers one line: “You have 1 Lyra message. Run lyra message check.” An idle Claude Code, Codex or OpenCode gets it typed at its ready prompt; a working agent gets it after its turn ends. The body stays in the mailbox.
  3. 0:05 A prints it with lyra message check, acts on it, then explicitly acknowledges the delivery.
  4. — A refused notice line is retried after 10 seconds. An unknown outcome is not retyped into the same execution.
  5. 1:00 B is a closed session. The Orchestrator sends B a message.
  6. 1:00 A closed or failed session refuses new mail unless its address was adopted; later sends then go to the adopter. If an unadopted recipient closes before handling accepted mail, the sender’s wait wakes with message-held.

Task delivery and turn binding

Section titled “Task delivery and turn binding”

Sessions in the picture: Orchestrator, Claude Worker

  1. 0:00 lyra-daemon types a request line before pasting the brief.
  2. 0:01 Claude Code wraps the pasted text.
  3. 0:02 lyra-daemon records the task it typed.
  4. 0:03 The status it reads from the Worker is stamped with that task, so progress is visible.
  5. — A turn it cannot match stays unknown; no match is guessed.
  6. 8:00 The Worker reports, completing the task and notifying its owner.

Tree shapes

Section titled “Tree shapes”

A Lead divides work and waits

Section titled “A Lead divides work and waits”

Sessions in the picture: Orchestrator, Lead, Worker, Worker

  1. 0:00 The Orchestrator assigns a large task with --role lead. The receiver is recorded as a Lead at depth 1. Omitting the role uses the default role in Orchestration settings.
  2. 0:30 The Lead calls worker start twice. Both Workers have depth 2.
  3. 0:31 The Lead’s turn ends while child tasks are running. It is Waiting{Workers}, not stalled, and its stall clock pauses.
  4. 9:05 The two Workers report in turn. Notifications go to the Lead.
  5. 9:06 Child work is complete. The Lead’s stall clock resumes from this point (lead_wait_ended_at).
  6. 10:20 The Lead reports the combined result to the Orchestrator.

A refused start and a higher depth limit

Section titled “A refused start and a higher depth limit”

Sessions in the picture: Person, Orchestrator, Lead, Worker · depth 2 → Lead · depth 2, Start Worker, Worker · depth 3

  1. 0:00 Orchestrator → Lead → Worker. This Worker has depth 2.
  2. 3:10 The Worker tries worker start to divide the work further.
  3. 3:10 lyra-daemon on this computer refuses the start. Workers cannot start any session, and depth 2 has also reached the limit. Nothing is created. The Worker asks its parent by message.
  4. 3:12 The Worker asks its Lead by message.
  5. 3:20 A person raises the depth limit to 3 in Orchestration settings and changes the Worker at depth 2 to a Lead. The entire live branch must satisfy the rules.
  6. 3:21 The Lead at depth 2 starts a Worker at depth 3. Raising the limit alone does not grant start permissions to a Worker.

Handoff and receipt acknowledgment

Section titled “Handoff and receipt acknowledgment”

Sessions in the picture: Orchestrator, Lead, Recipient

  1. 0:00 A Lead wants to hand an unstarted task it created to a new session (worker start --handoff).
  2. 0:01 The handoff message enters the recipient’s mailbox. message check only prints it; the receiving agent runs message ack to record receipt.
  3. 0:20 The receiver explicitly acknowledged the delivery, so it becomes the task owner before executing the task.
  4. 0:20 The new session receives the giver’s parent, depth and role. A Lead’s task goes to a Lead at depth 1.
  5. 0:20 The receiving Lead may divide the work. The giver is not added as a parent, so depth does not increase.
  6. — A never-claimed handoff returns at the 60-second deadline or on proven recipient closure. A claim without confirmed ack remains unknown and keeps the original owner until explicit resolution.
  7. — An existing receiver stays in place. For a running task, the executing Worker and its branch move beneath it.

A Lead starts an Orchestrator

Section titled “A Lead starts an Orchestrator”

Sessions in the picture: Orchestrator, Lead · depth 1, Worker, Orchestrator′, Worker · depth 2, Start Lead

  1. 0:00 The depth limit is 2. A Lead at depth 1 wants a separate line of work.
  2. 0:10 lyra orchestrator start --spec-file brief.md. lyra-daemon on this computer checks the role and permitted starters, records who started it, and delivers the brief with a request line and paste.
  3. 0:11 The new Orchestrator heads a new tree with no parent or assigned task. It still inherits the Lead’s depth of 1.
  4. 0:40 It starts a Worker at depth 2: allowed.
  5. 0:50 It tries to start a Lead: refused. A Lead must sit at depth 1 or shallower, but this child would have depth 2.
  6. — Workers cannot call this command. An agent’s lyra session open and lyra session continue follow the same rules. New Orchestrators and Leads must have room for children under the 8-step read cap.

Move a Worker to another Lead

Section titled “Move a Worker to another Lead”

Sessions in the picture: Orchestrator, Lead 1, Lead 2, Worker

  1. 0:00 The Worker works beneath Lead 1.
  2. 5:00 Lead 1 is busy with other work. A person (or the Orchestrator) moves this Worker beneath Lead 2.
  3. 5:00 lyra-daemon on this computer rechecks depth throughout the moving branch. The Worker still has depth 2, within the limit.
  4. 5:01 The move completes. This Worker’s task reports now go to Lead 2.
  5. — A Worker trying to move itself is refused. Sessions cannot reconnect themselves.
  6. — If the deepest session in the moving branch exceeds the limit, the entire move is refused.

Detach a Lead into a new tree

Section titled “Detach a Lead into a new tree”

Sessions in the picture: Orchestrator, Lead → Orchestrator″, Worker, Worker

  1. 0:00 The Lead has long-running work with two Workers.
  2. 1:00 The Orchestrator (or a person) detaches the Lead. The Lead cannot detach itself.
  3. 1:00 The Lead becomes an Orchestrator at depth 0 in a new tree. Both Workers become depth 1.
  4. — The task originally assigned to the Lead belongs to its parent. The Lead cannot hand it off as its own.
  5. — A person or the tree’s Orchestrator initiates this. The Lead cannot detach itself.

A Lead under a Lead — depth limit 3

Section titled “A Lead under a Lead — depth limit 3”

Sessions in the picture: Orchestrator, Person, Lead · depth 1, Start Lead, Lead · depth 2, Worker · depth 3, Worker · depth 3

  1. 0:00 Depth limit 2 (the default). Under the Orchestrator at depth 0, a Lead at depth 1 runs a large part. Its spec allows it one Lead of its own.
  2. 0:10 The Lead tries to give a sub-part to a --role lead session. The new Lead would stand at depth 2, and at limit 2 its children would have no room. lyra-daemon on this computer refuses it for the depth limit and creates nothing.
  3. 0:11 Following error.next, the Lead either gives that part to a Worker or asks its parent. Here it asks.
  4. 0:20 The person raises the depth limit to 3 in Settings → Orchestration. Agents cannot change this setting.
  5. 0:21 The Orchestrator answers and the Lead tries again. At limit 3 a Lead may stand at depth 2, so the new Lead starts there.
  6. 0:40 The depth-2 Lead starts two Workers. They stand at depth 3, the limit. A Worker starts no session wherever it stands.
  7. 1:30 Reports climb one step at a time: Worker → the depth-2 Lead → the depth-1 Lead → Orchestrator. Each Lead waits for its Workers like an Orchestrator; when its turn ends while they run, its parent reads it as waiting, not stopped.

Failure and recovery

Section titled “Failure and recovery”

A turn ends without a report (worker-stopped)

Section titled “A turn ends without a report (worker-stopped)”

Sessions in the picture: Orchestrator, Worker

  1. 0:00 The Worker is working, and the Orchestrator is inside task wait.
  2. 6:40 The Worker answers and ends its turn without calling lyra task report. The footer explains that stopping to speak is not a report.
  3. 6:41 The verdict is TurnEnded, which does not mean success; it is only a verdict. task wait wakes with worker-stopped.
  4. 6:42 The Orchestrator requests a report by urgent message (--urgent). The idle Worker receives a single notice line.
  5. 7:30 The Worker reports and the task completes. If its message was explicitly acknowledged after the turn ended, worker-stopped is suppressed.

Repeated failures exhaust the recovery budget

Section titled “Repeated failures exhaust the recovery budget”

Sessions in the picture: Orchestrator, Worker, lyra-supervisor

  1. 0:00 A transient server error stops the Worker.
  2. 0:02 Supervision enters “continue” in the same conversation (1/3). Backoff grows between 2 and 120 seconds.
  3. 0:40 Another failure, then continue (2/3).
  4. 2:30 Another failure, then continue (3/3). One recovery episode permits 3 steps, 3 model turns and 30 minutes.
  5. 4:10 The budget is exhausted. One notification tells the task owner the attempted steps and remaining budget. No further text is entered.
  6. — An authentication error would have notified immediately without continue. Permissions, invalid requests and quota failures behave the same way.

Take over after an Orchestrator ends

Section titled “Take over after an Orchestrator ends”

Sessions in the picture: old Orchestrator, new Orchestrator, Worker, Worker

  1. 0:00 The Orchestrator and its lyra-daemon ended. No one can manage its Workers’ tasks.
  2. 0:30 A person asks a new session to call lyra task adopt --from <old-session>. lyra-daemon on this computer requires evidence that the old owner ended.
  3. 0:31 Task ownership transfers and ownerGeneration increases. Ordinary unread and claimed mail moves to the adopter; later sends to the old address follow it. Pending handoffs to the ended receiver are abandoned. Worker depths stay the same.
  4. — An old Orchestrator returning to modify a task is refused because it is no longer the current owner.
  5. — lyra-daemon on this computer does not adopt automatically. A person must direct it.

worker start stops part-way

Section titled “worker start stops part-way”

Sessions in the picture: Orchestrator, Person, Worker

  1. 0:00 The Orchestrator calls worker start. That one call takes several steps in turn: it opens a session, creates the task and types the spec in.
  2. 0:20 The Worker’s agent shows a dialog asking whether to trust the folder. Nothing has been typed, and worker start stops because of the dialog (exit 1).
  3. 0:21 Read error.detail: failedStep is where it stopped, created is the session and task it already made (they stay; nothing is rolled back), and next is the exact command that continues this start.
  4. 0:21 Never run worker start again for it: each call creates new things and undoes nothing.
  5. 0:22 The Orchestrator asks the person to answer the dialog in that terminal.
  6. 1:10 Once the person has answered, run next with a new --request-id. The same Worker takes the task and starts working.

A Worker process dies

Section titled “A Worker process dies”

Sessions in the picture: Person, Orchestrator, lyra-supervisor, Worker A, Worker B, New Worker

  1. 0:00 The Orchestrator starts two Workers, runs task wait --all --timeout 15m in the background and ends its turn.
  2. 6:40 The agent process of Worker B ends suddenly. There is no report.
  3. 6:41 Lyra confirms that the process ended, and lyra-supervisor sends the task owner one escalation. A message ends the wait at once.
  4. 6:42 The Orchestrator handles confirmedCause and neededDecision, tells the person, then explicitly acknowledges the delivery. It does not cancel or reassign on its own.
  5. 7:30 On the person’s word, task cancel: the task of a Worker whose process ended reads stopped. Then task retry.
  6. 7:31 Run worker start --task <task-id> --workspace <workspace-id> --agent <name> for a fresh Worker in the same Workspace, or reuse one of your own idle Workers with terminal reuse. It keeps the stored spec and partial changes; send additional context by message.

A cancel is only a request

Section titled “A cancel is only a request”

Sessions in the picture: Person, Orchestrator, Worker

  1. 0:00 The person tells the Orchestrator to stop this task.
  2. 0:01 With the person’s word, the Orchestrator runs task cancel --yes. Lyra types one Ctrl-C into the Worker: a request, not a stop.
  3. 0:02 The Worker’s turn is cut off. The task still has its stop requested. The Orchestrator asks it by message to report stopped.
  4. 0:40 The Worker reports with task report --outcome stopped. Now the task reads stopped.
  5. 0:41 If the Worker cannot report, the task still reads stopped once Lyra proves its process ended. Keep waiting: a checkpoint lists the task once it has ended.
  6. 0:42 A task whose stop is unconfirmed cannot be retried. Tell the person; the Orchestrator or a Lead above the Worker can explicitly use session force-stop, which fails the attempt only after process termination is proven. Never start a duplicate task. Only a person may abandon an unconfirmed dispatch without proof.

Long-running work

Section titled “Long-running work”

A quiet Worker — suspect, stall, notification

Section titled “A quiet Worker — suspect, stall, notification”

Sessions in the picture: Orchestrator, Worker, lyra-supervisor

  1. 0:00 The Worker starts and progress signals arrive.
  2. 0:12 Signals stop. The process is still alive, but being alive is not progress.
  3. 10:12 No signal for 10 minutes: Suspect. The board shows No updates and the Orchestrator’s task wait wakes with worker-suspect. This is a status indication only.
  4. 60:12 At 60 minutes, StallBeyondLimit: lyra-supervisor sends one notification message to the task owner. Retrying after a restart uses the same request key and still counts once.
  5. 60:13 A person or the Orchestrator decides what comes next: ask by message, cancel, or retry.
  6. 61:00 When progress returns, the Suspect indication and notification status clear together.

An hour-long build — the no-news rule

Section titled “An hour-long build — the no-news rule”

Sessions in the picture: Person, Orchestrator, Worker, lyra-supervisor

  1. 0:00 The Worker starts the full build and tests. While its screen shows a running tool and a program under the agent uses CPU, Lyra counts that as progress. When the screen shows no running tool, or the tool’s program is idle, Lyra cannot tell a legitimate wait from a stall. The Orchestrator waits with task wait --all --timeout 15m.
  2. 10:00 After 10 minutes without a progress signal, worker-suspect arrives. A long build looks the same; on its own it proves nothing.
  3. 10:01 The Orchestrator looks once: the turn in status show, the changes in git status. The turn is still running and it is a long build, so it waits again.
  4. 40:01 At two checkpoints in a row the task shows the same state and progress: no news. The first time, it looks once more; the build is still running, so it waits.
  5. 55:01 No news again at the next checkpoint. It tells the person what it saw and keeps waiting. It never cancels, retries or re-dispatches on silence.
  6. 58:30 The build finishes and the Worker reports. When progress signals return, the No updates mark clears too.
  7. 58:31 If the agent’s screen or conversation file shows a running tool, then at the tool run limit (60 minutes by default) Lyra shows “Waiting too long” and sends one wait notification. That mark only tells. The existing 60-minute stall rule keeps running beside it, so a tool with no progress signal for that long is still reported. A person changes the separate limit in Settings; it applies after lyra-daemon on this computer restarts.

Links and remote

Section titled “Links and remote”

Disconnection and unknown dispatch

Section titled “Disconnection and unknown dispatch”

Sessions in the picture: Orchestrator, A runs while connected, B survive, C dispatching

  1. 0:00 Two Workers on a remote server. A runs only while connected; B keeps running after disconnection, which is the default.
  2. 4:00 Task C is being dispatched at that moment.
  3. 4:01 The link disconnects. A has a stop requested because the connection dropped. B continues and is observed again after reconnection.
  4. 4:01 Whether C received the text is unknown: unknown. It ends on its own only with evidence — a same-instance refusal from task.query, or confirmed termination of the recorded agent. It then becomes abandoned with mayHaveReached true.
  5. 9:30 The link returns. Cancellation is sent to A again.
  6. 9:31 Without evidence for C, only a person can end it with task retry --abandon-unproven. An agent is refused and told to ask the person. C’s old terminal is quarantined and not reused; closing that session is the person’s way out.

When the link drops — keep running or stop

Section titled “When the link drops — keep running or stop”

Sessions in the picture: Person, Orchestrator, A · stop, B · keep running

  1. 0:00 On disconnect in Settings → Orchestration is the default for new tasks. It starts as Keep running, and each task can set its own.
  2. 0:30 The Orchestrator gives two tasks to a remote server. A is made to run only while connected; B keeps running after disconnection, which is the default.
  3. 12:00 The link to that server drops. A’s task gets a stop request; B keeps running on the server.
  4. 12:01 While the link is down Lyra cannot see B’s status: worker-unobservable. That is not a result, so the wait starts again.
  5. 30:00 When the link returns, Lyra looks at B again and sends A the stop again.
  6. 30:01 A value set for a task wins over the default. Changing the default leaves tasks that already exist as they are.

A person in the loop

Section titled “A person in the loop”

Approval waits and Inbox

Section titled “Approval waits and Inbox”

Sessions in the picture: Orchestrator, Worker, Person

  1. 0:00 The Worker is working.
  2. 2:10 The Worker opens an approval dialog before deleting a file.
  3. 2:11 lyra-daemon on this computer treats this as a wait for a person (AwaitingHuman). It does not count it as a stall, and waits until the person answers.
  4. 2:12 Approvals for Lyra screen conversations go to Inbox. Terminal Workers receive answers in their terminals.
  5. 12:11 After the approval wait limit (10 minutes by default), the board shows “Waiting too long” and task wait returns a wait notification once. The decision is still the person’s; Lyra does not approve, stop, retry or escalate.
  6. 12:40 After the person approves, progress signals resume.

A person closes a Worker session

Section titled “A person closes a Worker session”

Sessions in the picture: Person, Orchestrator, Worker

  1. 0:00 The Orchestrator cancels the task (task cancel). A stop has been requested; termination is not yet confirmed.
  2. 0:30 A person closes that Worker session. Before closing it, lyra-daemon on this computer records the agent’s identity (PID and start time).
  3. 0:32 At the next status check, lyra-daemon on this computer asks that computer whether that identity is absent.
  4. 0:33 Confirmed absence changes the task to stopped. Retry, deletion and cancellation become available again.
  5. — If it is alive, unrecorded or unanswered, the task keeps its stop request without confirming termination. Unknown does not mean success.

A decision gate — held until the person chooses

Section titled “A decision gate — held until the person chooses”

Sessions in the picture: Person, Orchestrator, Gate, Worker · docs, Worker · API

  1. 0:00 The Orchestrator builds a plan: an API task, a UI task that waits for it, and a separate docs task. How to build the API is the person’s call.
  2. 0:05 The Orchestrator opens a gate on the API task (gate create): one question and at least two different options. A gate opens only on a task not yet given out, and holds it and the UI task after it.
  3. 0:06 The docs task is not held, so it goes out now. API and UI do not appear in task list --ready, and dispatching them is refused because they cannot start yet.
  4. 0:07 The Orchestrator asks the person in its conversation. A gate is not in Inbox, and the screens cannot answer it.
  5. 40:00 Forty minutes on, the gate is still open. Time passing is not a choice, and the Orchestrator does not decide without the person.
  6. 41:00 When the person answers, the Orchestrator records it, word for word as one of the options (gate resolve). The API task is released; the UI task waits for the API to finish.
  7. 41:01 Now the API task goes to a Worker. A running Worker’s question is answered by message, never with a gate.

Ask and receive the paired answer

Section titled “Ask and receive the paired answer”

Sessions in the picture: Person, Orchestrator, Worker

  1. 0:00 The Worker meets something its spec leaves open: delete the old config file or keep it. It asks instead of guessing.
  2. 4:10 The Worker runs message ask with its question and the task and attempt IDs. Its parent receives question mail with the question ID and the exact reply command.
  3. 4:11 The Orchestrator asks the person to decide. The Worker waits inside message ask, with a wait that fits its shell tool (--timeout 9m); the ask has already printed the question ID.
  4. 6:12 Still no answer: the ask ends and returns the question ID, and the question stays open. The Worker ends its turn, and that wait costs nothing; --resume would wait again. Asking is not reporting.
  5. 6:13 The Orchestrator’s wait wakes with worker-stopped. The question it just got is the stop, so it does not ask for a report and sends nothing but the answer.
  6. 9:00 The person answers. The Orchestrator runs message reply with the question ID and the answer, once.
  7. 9:01 No ask is waiting, so the answer arrives as message mail naming the question. The Worker prints and handles it, then explicitly acknowledges its delivery before waiting again. Without ack, the same batch replays.

Mixed agents

Section titled “Mixed agents”

Claude Code builds, Codex reviews

Section titled “Claude Code builds, Codex reviews”

Sessions in the picture: Orchestrator, Claude Code, Codex

  1. 0:00 The person wants a review as well. The Orchestrator starts the building Worker with --agent claude.
  2. 18:00 The building Worker reports: the files and commit, and its check results. That Worker keeps its terminal and context.
  3. 18:01 The review goes to a different agent than the builder: a review Worker starts with --agent codex.
  4. 26:00 The review Worker reports two things to fix.
  5. 26:01 The fixes go back to the builder, started with --keep-open so it stayed open after its report: a new task, given to the same terminal with terminal reuse. It remembers its work, so nothing starts from scratch.
  6. 31:00 Once the fixes are in, each Worker whose report was acknowledged closes by itself; only those started with --keep-open stay in the explorer. The final report gives the number kept and the agent, model and effort for each task; lyra terminal release frees them when the person asks.

An agent with little news

Section titled “An agent with little news”

Sessions in the picture: Person, Orchestrator, OpenCode

  1. 0:00 The Orchestrator starts a Worker with --agent opencode. OpenCode takes no --effort, so none is passed.
  2. 0:01 The result’s turn is not-started: the text was typed, but no turn signal has come. That can happen with an agent that sends few turn signals and is not a failure. It waits.
  3. 0:02 Lyra says it cannot see this Worker’s status: worker-unobservable. That is not a result, so it waits again.
  4. 30:02 No news at two checkpoints in a row. It looks once: git status shows no changes at all.
  5. 30:03 The text may still sit in its input box. The Orchestrator asks the person to look at that terminal. It never dispatches the task again or to a second Worker.
  6. 33:00 The person sees the waiting text and presses Enter. The text goes in and the Worker starts working.
  7. 51:20 The Worker reports. With this agent, only its report and the no-news rule tell you anything.
