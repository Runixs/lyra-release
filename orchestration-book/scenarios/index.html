시나리오

상태 낱말은 앱 화면과 같은 영어(Working, Waiting, Idle, Done)를 씁니다.

기본 흐름

섹션 제목: “기본 흐름”

두 Worker가 보고함

섹션 제목: “두 Worker가 보고함”

앱에서는 이 장면들을 그림과 함께 한 단계씩 재생했습니다. 이 페이지는 같은 단계를 차례대로 적습니다. 굵은 글씨는 장면의 시각이고, 「그림 속 세션」은 그 그림에 나온 상자의 이름입니다.

그림 속 세션: Orchestrator, Worker A, Worker B

  1. 0:00 Orchestrator가 worker start를 두 번 부릅니다. 둘 다 깊이 1입니다.
  2. 0:01 Orchestrator는 lyra task wait로 기다립니다. 터미널은 그 명령 안에서 조용히 멈춰 있습니다.
  3. 8:12 A가 보고합니다. 이 컴퓨터의 lyra-daemon이 작업 A를 끝내고 알림을 넣고, task wait가 message로 깨어납니다.
  4. 8:13 Orchestrator가 결과를 처리하고 배달을 명시적으로 ack한 뒤 task wait를 다시 실행합니다.
  5. 11:40 B가 보고합니다. 같은 길로 알림이 옵니다.
  6. 11:41 기다릴 작업도 메시지도 없으면 task wait는 두 번째 빈 확인에서 idle을 줍니다.

메시지 배달 — 쉬는 에이전트와 닫힌 세션

섹션 제목: “메시지 배달 — 쉬는 에이전트와 닫힌 세션”

그림 속 세션: Orchestrator, Worker A, Worker B

  1. 0:00 Orchestrator가 쉬는 A에게 급한 메시지를 보냅니다 (--urgent). 급하지 않은 메시지는 설정한 시간(기본 5분)까지 모았다가 함께 전합니다.
  2. 0:01 이 컴퓨터의 lyra-daemon이 받는 쪽마다 알림 하나를 잡고, 세션이 도는 컴퓨터의 lyra-daemon이 한 줄만 전합니다: “You have 1 Lyra message. Run lyra message check.” 쉬는 Claude Code와 Codex, OpenCode는 준비된 프롬프트에 입력된 줄로 받고, 일하는 에이전트는 턴이 끝난 뒤 받습니다. 본문은 우편함에 남습니다.
  3. 0:05 A가 lyra message check로 출력하고 메시지대로 행동한 뒤 배달을 명시적으로 ack합니다.
  4. — 알림 줄이 거절되면 10초 뒤에 다시 칩니다. 결과를 모르면(unknown) 같은 실행에는 다시 치지 않습니다.
  5. 1:00 B는 닫힌 세션입니다. Orchestrator가 B에게 메시지를 보냅니다.
  6. 1:00 닫혔거나 실패한 세션은 새 메시지를 거절합니다. 주소가 입양되었다면 이후 메시지는 입양한 세션으로 갑니다. 받아 둔 메시지를 처리하기 전에 입양되지 않은 받는 쪽이 닫히면 보낸 쪽의 기다림이 message-held로 깨어납니다.

작업 배달과 턴 연결

섹션 제목: “작업 배달과 턴 연결”

그림 속 세션: Orchestrator, Claude Worker

  1. 0:00 lyra-daemon이 요청 한 줄을 먼저 치고 작업 글을 붙여넣습니다.
  2. 0:01 Claude Code가 붙여넣은 글을 포장합니다.
  3. 0:02 lyra-daemon이 자신이 쳐 넣은 작업을 기록합니다.
  4. 0:03 Worker에게서 읽은 상태에 그 작업을 표시하므로 진행이 보입니다.
  5. — 맞출 수 없는 턴은 unknown으로 두고, 추측해서 묶지 않습니다.
  6. 8:00 Worker가 보고하면 작업이 끝나고 주인에게 알림이 갑니다.

나무 모양

섹션 제목: “나무 모양”

Lead가 나눠 맡기고 기다림

섹션 제목: “Lead가 나눠 맡기고 기다림”

그림 속 세션: Orchestrator, Lead, Worker, Worker

  1. 0:00 Orchestrator가 –role lead로 큰 일을 맡깁니다. 받은 세션은 깊이 1의 Lead로 기록됩니다. 역할을 생략하면 설정의 기본 역할을 씁니다.
  2. 0:30 Lead가 worker start를 두 번 부릅니다. 두 Worker는 깊이 2입니다.
  3. 0:31 Lead의 턴이 끝납니다. 하위 작업이 진행 중이라 멈춤이 아니라 Waiting{Workers}입니다. 멈춤 시계도 돌지 않습니다.
  4. 9:05 두 Worker가 차례로 보고합니다. 알림은 Lead에게 갑니다.
  5. 9:06 하위 작업이 끝났습니다. Lead의 멈춤 시계는 이때부터 다시 잽니다 (lead_wait_ended_at).
  6. 10:20 Lead가 합친 결과를 Orchestrator에게 보고합니다.

깊이 한도가 시작을 거절하고, 한도를 올리면 허용

섹션 제목: “깊이 한도가 시작을 거절하고, 한도를 올리면 허용”

그림 속 세션: 사람, Orchestrator, Lead, Worker · 깊이 2 → Lead · 깊이 2, Worker 시작, Worker · 깊이 3

  1. 0:00 Orchestrator → Lead → Worker. 이 Worker는 깊이 2입니다.
  2. 3:10 Worker가 일을 더 나누려고 worker start를 부릅니다.
  3. 3:10 이 컴퓨터의 lyra-daemon이 시작을 거절합니다. Worker는 아무 세션도 시작할 수 없고, 깊이 2에서는 한도에도 닿았습니다. 아무것도 만들지 않습니다. 부모에게 메시지로 물어봅니다.
  4. 3:12 Worker가 Lead에게 메시지로 묻습니다.
  5. 3:20 사람이 설정에서 깊이 한도를 3으로 올리고 깊이 2의 Worker를 Lead로 바꿉니다. 살아 있는 가지 전체가 규칙에 맞아야 합니다.
  6. 3:21 깊이 2의 Lead가 깊이 3의 Worker를 시작합니다. 한도만 올려도 Worker 역할의 시작 권한이 생기지는 않습니다.

인계와 읽음 확인

섹션 제목: “인계와 읽음 확인”

그림 속 세션: Orchestrator, Lead, 받는 세션

  1. 0:00 Lead가 자기가 만든 아직 시작 안 한 작업을 새 세션에 넘기려 합니다 (worker start --handoff).
  2. 0:01 인계 메시지가 받는 세션에 들어갑니다. message check는 출력만 합니다. 받는 쪽이 message ack를 실행해야 수신이 확인됩니다.
  3. 0:20 받는 쪽이 배달을 명시적으로 확인했으므로 작업을 실행하기 전에 작업 주인이 바뀝니다.
  4. 0:20 새 세션은 준 쪽과 같은 부모, 같은 깊이, 같은 역할로 작업을 받습니다. Lead가 준 작업이면 깊이 1의 Lead입니다.
  5. 0:20 받은 Lead가 작업을 나눠 맡길 수 있습니다. 인계한 쪽을 부모로 덧붙이지 않으므로 깊이가 늘지 않습니다.
  6. — 한 번도 가져가지 않은 인계는 60초가 지나거나 받는 세션이 닫혔다고 증명되면 돌아옵니다. 가져갔지만 ack가 확인되지 않으면 결과를 알 수 없으며 명시적으로 해결할 때까지 기존 주인을 유지합니다.
  7. — 이미 있는 세션에게 주면 그 세션은 제자리에 있고, 도는 작업이면 하던 Worker가 가지째 그 밑으로 갑니다.

Lead가 새 Orchestrator를 시작

섹션 제목: “Lead가 새 Orchestrator를 시작”

그림 속 세션: Orchestrator, Lead · 깊이 1, Worker, Orchestrator′, Worker · 깊이 2, Lead 시작

  1. 0:00 깊이 한도 2. Lead(깊이 1)가 따로 굴러갈 일 줄기를 열고 싶습니다.
  2. 0:10 lyra orchestrator start –spec-file brief.md. 이 컴퓨터의 lyra-daemon이 역할과 허용된 시작 주체를 확인하고 누가 시작했는지 적습니다. 요청 줄과 붙여넣기로 브리프를 전합니다.
  3. 0:11 새 Orchestrator는 새 나무의 꼭대기라 부모도 받은 작업도 없습니다. 하지만 Lead의 깊이(1)에서 시작합니다.
  4. 0:40 Worker를 시작합니다 (깊이 2): 됩니다.
  5. 0:50 Lead를 시작하려 하면 거절됩니다. Lead는 깊이 1까지인데 자식은 깊이 2이기 때문입니다.
  6. — Worker는 이 명령을 부를 수 없습니다. 에이전트의 lyra session open과 lyra session continue도 같은 규칙입니다. 새 Orchestrator와 Lead는 자기 자식까지 8단계 읽기 상한 안에 들어가야 합니다.

Worker를 다른 Lead로 옮김

섹션 제목: “Worker를 다른 Lead로 옮김”

그림 속 세션: Orchestrator, Lead 1, Lead 2, Worker

  1. 0:00 Worker가 Lead 1 밑에서 일합니다.
  2. 5:00 Lead 1이 다른 일로 바빠서, 사람이(또는 Orchestrator가) 이 Worker를 Lead 2 밑으로 옮깁니다.
  3. 5:00 이 컴퓨터의 lyra-daemon이 옮길 가지 전체의 깊이를 다시 잽니다. Worker는 여전히 깊이 2, 한도 안입니다.
  4. 5:01 옮겼습니다. 이 Worker 작업의 보고는 이제 Lead 2로 갑니다.
  5. — Worker가 스스로 옮기려 하면 거절됩니다. 세션은 자기를 다시 잇지 못합니다.
  6. — 가지째 옮길 때 가지에서 가장 깊은 세션이 한도를 넘으면 전체를 거절합니다.

Lead를 떼어 새 나무로

섹션 제목: “Lead를 떼어 새 나무로”

그림 속 세션: Orchestrator, Lead → Orchestrator″, Worker, Worker

  1. 0:00 Lead가 Worker 둘과 오래 갈 일을 맡았습니다.
  2. 1:00 Orchestrator(또는 사람)가 Lead를 떼어냅니다. 그 Lead 자신은 할 수 없습니다.
  3. 1:00 Lead가 새 나무의 Orchestrator(깊이 0)가 됩니다. 두 Worker는 깊이 1이 됩니다.
  4. — Lead가 원래 부모에게서 받은 작업은 부모의 것입니다. Lead가 자기 작업인 것처럼 인계할 수 없습니다.
  5. — 사람이나 나무의 Orchestrator가 시작합니다. 그 Lead 자신은 스스로 떼어낼 수 없습니다.

Lead 아래 Lead — 깊이 한도 3

섹션 제목: “Lead 아래 Lead — 깊이 한도 3”

그림 속 세션: Orchestrator, 사람, Lead · 깊이 1, Lead 시작, Lead · 깊이 2, Worker · 깊이 3, Worker · 깊이 3

  4. 0:33 없음이 확인되면 작업은 stopped. 다시 시도, 지우기, 취소를 다시 할 수 있습니다.
  5. — 살아 있거나, 기록이 없거나, 답이 없으면 중지를 요청한 상태로 둡니다. 모르는 것은 성공이 아닙니다.

갈림길 — 사람이 고를 때까지 멈춤

섹션 제목: “갈림길 — 사람이 고를 때까지 멈춤”

그림 속 세션: 사람, Orchestrator, 갈림길, Worker · 문서, Worker · API

  1. 0:00 Orchestrator가 계획을 세웁니다: API 작업, 그것을 기다리는 UI 작업, 따로 도는 문서 작업. API를 어떻게 할지는 사람이 정할 일입니다.
  2. 0:05 Orchestrator가 API 작업에 갈림길을 엽니다 (gate create): 질문 하나와 서로 다른 선택지 둘 이상. 갈림길은 아직 맡기지 않은 작업에만 열고, 그 작업과 뒤따르는 UI 작업을 붙잡습니다.
  3. 0:06 붙잡히지 않은 문서 작업은 바로 맡깁니다. API와 UI는 task list --ready에 나오지 않고, 맡기려 하면 아직 시작할 수 없다며 거절됩니다.
  4. 0:07 Orchestrator가 대화에서 사람에게 묻습니다. 갈림길은 받은 요청에 나오지 않고, 화면에서 답할 수도 없습니다.
  5. 40:00 40분이 지나도 갈림길은 열려 있습니다. 시간이 지나는 것은 선택이 아니고, Orchestrator는 사람의 답 없이 정하지 않습니다.
  6. 41:00 사람이 답하면 Orchestrator가 그 답을 선택지와 똑같은 글로 기록합니다 (gate resolve). API 작업이 풀리고, UI 작업은 API가 끝나기를 기다립니다.
  7. 41:01 이제 API 작업을 Worker에게 맡깁니다. 도는 Worker의 질문에는 갈림길이 아니라 메시지로 답합니다.

질문하고 연결된 답변 받기

섹션 제목: “질문하고 연결된 답변 받기”

그림 속 세션: 사람, Orchestrator, Worker

  1. 0:00 Worker가 일하다가 명세가 정하지 않은 것을 만납니다: 옛 설정 파일을 지울지 남길지. 추측하지 않고 묻습니다.
  2. 4:10 Worker가 질문과 작업·시도 ID로 message ask를 실행합니다. 부모는 질문 ID와 정확한 답변 명령이 담긴 질문 메시지를 받습니다.
  3. 4:11 Orchestrator가 사람에게 결정을 묻습니다. Worker는 셸 도구 한도에 맞춘 대기(–timeout 9m)로 message ask에서 답을 기다립니다. ask는 질문 ID를 이미 알려 주었습니다.
  4. 6:12 아직 답이 없습니다. ask는 질문 ID를 돌려주고 끝나며, 질문은 열린 채 남습니다. Worker는 턴을 끝내고, 그 기다림에는 비용이 들지 않습니다. –resume으로 다시 기다릴 수도 있습니다. 질문은 보고가 아닙니다.
  5. 6:13 Orchestrator의 대기가 worker-stopped로 깨어납니다. 방금 받은 질문이 멈춘 이유이므로 보고를 요구하지 않고, 답 말고는 보내지 않습니다.
  6. 9:00 사람이 답합니다. Orchestrator가 질문 ID와 답변으로 message reply를 한 번 실행합니다.
  7. 9:01 기다리는 ask가 없으면 질문을 가리키는 메시지로 답이 도착합니다. Worker가 출력하고 처리한 뒤 배달을 명시적으로 ack하고 다시 기다립니다. ack하지 않으면 같은 묶음이 다시 나옵니다.
