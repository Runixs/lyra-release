엣지 케이스

드물지만 생기면 헷갈리는 경우들입니다. 영역으로 거르고, 낱말로 찾을 수 있습니다.

깊이·역할

섹션 제목: “깊이·역할”

Worker가 lyra session open + lyra session prompt로 깊이 한도를 피함

섹션 제목: “Worker가 lyra session open + lyra session prompt로 깊이 한도를 피함”

에이전트의 lyra session open과 lyra session continue는 새 Orchestrator 시작과 같은 규칙입니다. Worker는 거절합니다. session prompt는 자기 나무 안이나 자기가 시작한 세션에만 쓸 수 있습니다.

인계가 돌아서 고리가 됨 (A → B → A)

섹션 제목: “인계가 돌아서 고리가 됨 (A → B → A)”

인계는 부모 선을 더하지 않습니다. 도는 작업을 하던 Worker의 가지 안으로 넘기는 것은 고리로 거절합니다.

다른 나무에서 이미 더 깊은 세션에게 인계

섹션 제목: “다른 나무에서 이미 더 깊은 세션에게 인계”

받는 쪽은 제자리에서 주인이 됩니다. 하던 Worker가 가지째 그 밑으로 가고, 가지 전체가 깊이 한도 안에 들어가야 합니다.

돌고 도는 사슬을 깊이 상한 8에서 읽음

섹션 제목: “돌고 도는 사슬을 깊이 상한 8에서 읽음”

8 단계에서 읽기를 멈추고 한도를 넘은 것으로 봅니다. 그래서 설정 최대값이 7입니다.

옮기면 한도를 넘는 경우

섹션 제목: “옮기면 한도를 넘는 경우”

가지 전체를 다시 재서 한 세션이라도 넘으면 옮기기 전체를 거절합니다.

자식이 있는 Lead를 Worker로 내림

섹션 제목: “자식이 있는 Lead를 Worker로 내림”

살아 있는 자식이 없을 때만 됩니다. 있으면 거절하고 먼저 자식을 끝내거나 옮기라고 합니다.

Lead가 만든 새 Orchestrator가 Lead를 시작

섹션 제목: “Lead가 만든 새 Orchestrator가 Lead를 시작”

새 Orchestrator는 그 Lead의 깊이(1)에 섭니다. 한도 2면 자식이 깊이 2라 Lead 자리가 아니어서 거절합니다.

한도 1에서 Lead 시작

섹션 제목: “한도 1에서 Lead 시작”

Lead가 설 자리(깊이 ≤ 0)가 없어 거절합니다. Orchestrator는 Worker만 시작합니다.

Worker가 --role lead로 시작하려 함

섹션 제목: “Worker가 --role lead로 시작하려 함”

Worker는 아무것도 시작하지 않으므로 역할과 상관없이 거절합니다.

배달

섹션 제목: “배달”

작업 글이 16 KiB를 넘음

섹션 제목: “작업 글이 16 KiB를 넘음”

계획에는 256 KiB까지 적히지만 터미널에 칠 때 16 KiB를 넘으면 거절됩니다. 긴 브리프는 파일에 두고 그 경로를 말하게 합니다.

bracketed paste를 본 적 없는 에이전트에 여러 줄

섹션 제목: “bracketed paste를 본 적 없는 에이전트에 여러 줄”

여러 줄 입력을 안전하게 넣을 수 있는지 확인하지 못하면 거절합니다. 꼬리말이 한 줄인 까닭입니다.

Claude가 붙여넣기 포장을 또 바꿈

섹션 제목: “Claude가 붙여넣기 포장을 또 바꿈”

엄격하게 벗기지 못하면 묶지 않고 unknown으로 둡니다 (노란 ?). 추측해서 묶지 않습니다.

사람이 그 Worker 창에서 치는 중

섹션 제목: “사람이 그 Worker 창에서 치는 중”

입력칸에 글이 남아 있으면 지워질 때까지 작업을 치지 않고, 준비되지 않았다는 거절로 끝날 수 있습니다. 그 기다림이 끝나면 막지 않고 그대로 치며, 사람이 치는 글과 섞일 수 있습니다. 메시지 알림과 복구 continue는 입력칸을 기다리지 않으므로, 그 Enter가 사람이 남긴 글까지 보낼 수 있습니다.

입력칸을 읽을 수 없는 에이전트

섹션 제목: “입력칸을 읽을 수 없는 에이전트”

기다리지 않고 칩니다. 알려진 대화 상자가 떠 있으면 그래도 거절합니다.

알림 줄의 결과를 모름 (unknown)

섹션 제목: “알림 줄의 결과를 모름 (unknown)”

같은 실행에는 다시 치지 않습니다. 옛 입력이 끝났다고 증명할 수 없기 때문이며, 다른 확인된 실행이 와야 풀립니다. 보낸 쪽의 기다림은 message-held로 깨어나니, 다시 보내지 말고 message show와 session show를 본 뒤 그래도 모르면 사람에게 묻습니다.

닫힌 세션에 메시지

섹션 제목: “닫힌 세션에 메시지”

닫혔거나 실패한 세션으로 보내면 주소가 입양되지 않은 한 거절됩니다. 입양 뒤의 새 일반 메시지는 입양한 세션으로 갑니다. 그 외에는 열린 세션을 고릅니다.

지켜보기

섹션 제목: “지켜보기”

Lyra가 상태를 읽을 수 없는 에이전트

섹션 제목: “Lyra가 상태를 읽을 수 없는 에이전트”

턴을 작업에 묶을 상태가 없어 진행이 비고, task wait는 worker-stopped를 내지 않습니다. 증거가 없으니 10분에 Suspect, 60분에 멈춤 알림이 갑니다.

승인 대화 상자에서 Esc — Stop이 오지 않음

섹션 제목: “승인 대화 상자에서 Esc — Stop이 오지 않음”

승인 대기에는 사람이 답해야 합니다. 대화 상자를 닫았는데도 기다림으로 남으면 실제 세션을 확인하고 주인에게 알립니다.

Lead가 앞에서 task wait를 부른 채 기다림

섹션 제목: “Lead가 앞에서 task wait를 부른 채 기다림”

앞에서 실행 중인 task wait은 도구 실행입니다. 도구 실행 한도 뒤 기다림 알림으로 부모에게 한 번 알릴 수 있지만 Lead를 중지·재시도·상신하지 않습니다. 턴이 끝났어도 하위 작업이 돌면 Waiting{Workers}이며, 이 역시 멈춤이 아닙니다.

로그인 오류

섹션 제목: “로그인 오류”

사람의 결정이 필요하므로 continue를 치지 않고 바로 알립니다. 권한, 잘못된 요청, 모델 거절, 할당량도 같습니다.

프로세스가 끝남

섹션 제목: “프로세스가 끝남”

끝났음이 확인될 때만 공급자 세션을 이어 갑니다. 확인 못 하면 알립니다.

인계·입양

섹션 제목: “인계·입양”

Orchestrator가 사라진 뒤 넘겨받기

섹션 제목: “Orchestrator가 사라진 뒤 넘겨받기”

새 세션이 task adopt --from으로 넘겨받습니다. 옛 주인이 끝났다는 증거가 있어야 하고, 소유권 세대가 올라 옛 주인의 요청은 거절됩니다. 넘겨받아도 Worker들의 깊이는 그대로입니다.

받는 쪽이 60초 안에 읽지 않음

섹션 제목: “받는 쪽이 60초 안에 읽지 않음”

한 번도 가져가지 않은 인계는 시간이 지나거나 받는 세션이 닫히거나 작업 시도가 끝나면 주인이 준 쪽으로 돌아갑니다. 가져갔지만 ack가 확인되지 않으면 결과를 알 수 없으며 명시적으로 해결할 때까지 주인은 그대로입니다.

연결 중에만 실행하는 작업에 worker start --handoff

섹션 제목: “연결 중에만 실행하는 작업에 worker start --handoff”

인계한 작업은 연결에 매여 있으면 안 되므로 거절합니다.

연결·unknown

섹션 제목: “연결·unknown”

원격 컴퓨터의 lyra-daemon이 오래됨

섹션 제목: “원격 컴퓨터의 lyra-daemon이 오래됨”

깊이, 역할, 지켜보기 시간은 이 컴퓨터의 lyra-daemon이 적용합니다. 작업 배달과 턴 연결에는 해당 동작을 지원하는 세션이 도는 컴퓨터의 lyra-daemon이 필요합니다. 묶을 증거가 없으면 unknown으로 둡니다.

에이전트가 --abandon-unproven을 부름

섹션 제목: “에이전트가 --abandon-unproven을 부름”

종료 증거 없이 작업을 포기하는 것은 사람만 할 수 있으므로 거절하고 사람에게 물으라고 합니다.

격리된 Worker 터미널

섹션 제목: “격리된 Worker 터미널”

다시 쓰기와 놓기를 거절하고 그 세션으로의 배차도 거절합니다. 사람이 그 세션을 닫는 것이 출구입니다.

보고

섹션 제목: “보고”

다시 시도한 뒤 늦게 온 보고

섹션 제목: “다시 시도한 뒤 늦게 온 보고”

옛 시도의 보고는 StaleAttempt로 이름 붙여 거절합니다. “적용 안 됨”으로 흐리지 않습니다.

같은 Worker가 두 번 보고

섹션 제목: “같은 Worker가 두 번 보고”

받아들여진 첫 보고만 알림을 보냅니다.

다시 맡기는 횟수 한도를 넘음 (계획)

섹션 제목: “다시 맡기는 횟수 한도를 넘음 (계획)”

시도 횟수에 닿으면 배차나 다시 시도가 거절됩니다. 작업에 적용된 한도를 확인합니다.

설정

섹션 제목: “설정”

더 깊은 세션이 도는 중에 깊이 한도를 낮춤

섹션 제목: “더 깊은 세션이 도는 중에 깊이 한도를 낮춤”

도는 세션은 그대로 둡니다. 새 시작만 새 한도로 거절합니다. 설정 화면이 “깊이 N에서 도는 세션 K개” 경고를 보여 줍니다.

저장된 깊이 값이 깨짐 (숫자가 아님, 0, 8 이상)

섹션 제목: “저장된 깊이 값이 깨짐 (숫자가 아님, 0, 8 이상)”

기본값 2로 돌아갑니다. 깨진 값이 한도를 없애는 길이 되지 않게 합니다.

에이전트가 자기 깊이 한도를 올리려 함

섹션 제목: “에이전트가 자기 깊이 한도를 올리려 함”

거절됩니다. 설정 동작은 화면(renderer)만 부를 수 있게 등록하고 CLI 쓰기 동사를 두지 않습니다. 이 컴퓨터의 lyra-daemon도 에이전트 호출 문맥이 있는 쓰기를 거절합니다. 거절 글은 사람에게 설정을 바꿔 달라고 하라고 말합니다.

“사람인지”는 보안 경계가 아님

섹션 제목: ““사람인지”는 보안 경계가 아님”

LYRA_SESSION_ID가 없는 호출을 사람으로 봅니다. 에이전트가 그 변수를 지우고 CLI를 부르면 사람처럼 보입니다. 그래서 설정은 CLI 쓰기를 아예 두지 않습니다.

No updates 시간 ≥ 멈춤 알림 시간

섹션 제목: “No updates 시간 ≥ 멈춤 알림 시간”

설정값이 허용 범위를 벗어나면 거절합니다. 0이나 7일 이상도 거절합니다. 화면에서는 고를 수 없게 막고, 그래도 오면 줄 아래 붉은 글로 보입니다.

두 창에서 동시에 바꿈

섹션 제목: “두 창에서 동시에 바꿈”

설정의 변경 이력을 비교해 이전 값을 바탕으로 한 저장을 거절합니다. 화면은 새 값을 다시 읽어 보여 줍니다.

지켜보기 시간을 바꿨는데 그대로임

섹션 제목: “지켜보기 시간을 바꿨는데 그대로임”

저장은 바로 되지만 이 컴퓨터의 lyra-daemon이 다시 시작될 때 적용됩니다 (restartRequired). 화면은 “다시 시작해야 적용”을 보여 줍니다.

동시 Worker 수 제한에 닿음 (켰을 때)

섹션 제목: “동시 Worker 수 제한에 닿음 (켰을 때)”

새 Worker 시작을 거절하고 지금 도는 수와 한도를 알려 줍니다. 기본은 꺼짐.
