문제 해결

문제는 어디에 나타나나요

섹션 제목: “문제는 어디에 나타나나요”
  1. 알림(벨) — 화면 위쪽의 벨을 엽니다. 지금 문제에 지금 확인된 문제가, 지난 알림에 이전 알림이 있습니다. 알림은 지우기 전까지 남고, 지워도 Session의 기록은 그대로입니다.
  2. 문제 기록 — 설정 → 정보 → 문제 기록에 앱과 서버에서 생긴 오류, 경고, 안내가 모입니다. 30일이 지나거나 5,000건을 넘으면 오래된 기록부터 지웁니다. 종류와 영역으로 거르고, 내용이나 코드로 찾을 수 있습니다.
  3. 기술 정보 복사 — 기록 하나를 열면 이 버튼이 있습니다. 복사한 글에서 경로, 환경 값, 비밀, 명령은 ‹가림›으로 가려집니다.
  4. 로그 폴더 열기 — 같은 화면에서 로그 폴더를 엽니다. Windows에서는 %LOCALAPPDATA%\Lyra\logs이고, 파일은 main.log입니다.
  5. lyra doctor — 터미널에서 실행하는 점검 명령입니다. 읽기만 하고 아무것도 고치지 않습니다. 점검 하나당 5초까지 기다리고, 한 줄에 점검 하나와 상태(ok, warning, unreachable, unread)를 보여 줍니다.

lyra-daemon(이 컴퓨터에서 Session을 돌리는 Lyra의 엔진 프로그램)이 떠 있는지만 보려면 lyra daemon status를 실행합니다. 켜져 있으면 running과 버전이 나오고, 꺼져 있으면 not-running이 나옵니다. 이 명령은 엔진을 시작하지 않습니다.

기록을 저장하지 못하면 “문제 기록을 남기지 못하고 있습니다”라고 알립니다. 앱은 계속 쓸 수 있지만 디스크 여유 공간과 폴더 권한을 확인하세요.

Failed · Unverified Session

섹션 제목: “Failed · Unverified Session”

Failed · Unverified는 시작에 실패한 것은 알지만, 처음 시작한 프로세스가 멈췄는지 확인하지 못한 상태입니다. 컴퓨터 어딘가에 에이전트 프로세스가 남아 있을 수 있습니다.

  1. 같은 Session을 쓰던 컴퓨터에서 에이전트 프로세스가 남아 있는지 확인합니다.
  2. 남아 있으면 먼저 끝냅니다.
  3. Lyra에서 그 Session을 닫습니다. 확인하지 못한 세션을 닫을까요? 창이 뜨면 확인 없이 닫기를 누릅니다.

닫아도 프로세스가 멈추는 것은 아닙니다. 기록에만 **Closed (unverified)**로 남습니다. 이 상태의 Session은 스스로 끝난 것으로 세지 않습니다. 이 Session이 쓰던 작업 자리를 정리하려 하면 막힐 수 있습니다.

에이전트가 바로 종료될 때

섹션 제목: “에이전트가 바로 종료될 때”

에이전트 화면에 “에이전트가 종료되었습니다 (종료 코드 …)“가 나오고 다시 시작 버튼이 보입니다. 종료 코드를 알 수 없으면 “(종료 코드 확인 불가)”, 강제로 끝났으면 “에이전트가 강제로 종료되었습니다”라고 나옵니다. 벨에도 작업 프로세스 끝남이 올라옵니다.

  1. 종료 코드를 적어 둡니다.
  2. 프로필에 실행 전 명령이 있으면, 그 단계가 실패했다는 안내(종료 코드 포함)가 따로 나올 수 있습니다. 명령을 고친 뒤 테스트하세요.
  3. 설정 → 에이전트에서 프로필을 열고 테스트 탭을 실행해 어느 단계에서 멈추는지 봅니다. 단계는 실행 전 명령, 에이전트 시작, 모델 확인 순서입니다.
  4. 이유를 모르겠으면 문제 기록에서 기술 정보 복사를 하고 문제 알리기를 보세요.

버전 확인이 끝나지 않을 때

섹션 제목: “버전 확인이 끝나지 않을 때”

“… 버전 확인이 … 초 안에 끝나지 않았습니다”가 설정 → 에이전트에 나옵니다. 프로필이 래퍼 스크립트(다른 프로그램을 감싸서 대신 실행하는 스크립트)를 실행하게 되어 있으면 버전을 늦게 돌려줘서 이렇게 될 수 있습니다.

Lyra는 처음 5초, 다시 시도에서 8초를 기다립니다. 정확한 실행 파일 경로를 지정한 확인은 8초입니다.

  1. 컴퓨터가 바쁘면 잠시 뒤 지금 확인을 누릅니다.
  2. 두 번 모두 끝나지 않았다면 그 컴퓨터의 터미널에서 에이전트 명령이 바로 실행되고 버전을 출력하는지 확인합니다.
  3. 프로필의 실행 파일이 래퍼 스크립트라면, 그 스크립트가 버전을 5초 안에 출력하는지 터미널에서 먼저 재 보세요. 느리면 에이전트 본체의 절대 경로를 **실행 파일 (절대 경로)**에 적습니다.
  4. 세션을 열 때 “버전을 읽지 못해 세션을 열지 않았습니다”가 나오면, 같은 방법으로 실행 파일이 실행되고 버전을 출력하는지 확인한 뒤 에이전트를 다시 확인합니다.

서버 로그인이 안 되거나 시간이 초과될 때

섹션 제목: “서버 로그인이 안 되거나 시간이 초과될 때”

서버가 인증을 거부했습니다 — 서버 설정이나 로그인 상태를 확인한 뒤 다시 시도합니다.

  1. 설정 → 연결 → 원격에서 서버 줄을 엽니다.
  2. 비밀번호를 쓰는 서버라면 비밀번호 고치기로 새로 입력한 뒤 입력하고 연결을 누릅니다.
  3. ~/.ssh/config 별칭으로 추가한 서버는 이 컴퓨터의 ssh 설정을 씁니다. 그 설정과 키를 먼저 확인하세요. 같은 서버에 터미널에서 ssh <별칭>으로 들어가 보면 원인을 나눠 볼 수 있습니다.
  4. 연결을 다시 누릅니다.

인증 결과를 기한 안에 받지 못했습니다 — 서버가 답을 주지 않은 경우입니다.

  • 서버의 각 응답은 10초, 비밀번호 로그인에서 사람이 입력하는 시간을 뺀 전체는 30초까지 기다립니다. 일회용 코드를 보낸 뒤의 응답만은 그 30초 가운데 남은 시간까지 기다립니다. 회사 게이트웨이가 코드를 확인하느라 10초를 넘겨도 로그인이 끊기지 않게 하려는 것입니다.
  • 코드를 보낸 뒤에도 게이트웨이가 끝내 답하지 않으면 「회사 게이트웨이 … 가 서버 “…” 로그인에서 일회용 코드를 받은 뒤 …초 동안 답하지 않았습니다. 코드를 거절한 것이 아니라 게이트웨이가 느린 것일 수 있습니다. 새 코드로 다시 연결하세요. 저장한 사내 ID 비밀번호는 그대로 둡니다.」가 나옵니다. 저장한 비밀번호는 지우지 않으니, 연결을 다시 눌러 새 코드를 넣으면 됩니다.
  • 사람이 비밀번호나 일회용 코드를 입력하는 시간은 이 한도에 넣지 않습니다.
  • 서버가 일회용 코드를 요구하는데 Lyra가 묻지 못하는 경우에는, 터미널에서 ssh로 직접 접속해 코드를 입력하라는 안내가 나옵니다.

서버에 lyra-daemon을 설치하지 못할 때

섹션 제목: “서버에 lyra-daemon을 설치하지 못할 때”

처음 연결하는 서버나 아직 이 버전이 없는 서버에는, 이 컴퓨터가 Lyra가 업데이트를 받는 곳에서 서버 패키지를 내려받아 올립니다. 이미 이 버전이 깔린 서버는 내려받기를 기다리지 않습니다.

안내 할 일
「…이 컴퓨터가 Lyra가 업데이트를 받는 곳에서 이 버전의 서버 패키지를 내려받지 못했고, 이 컴퓨터에 그 사본도 없습니다.」 네트워크가 될 때 다시 연결합니다. 네트워크가 없으면 다른 컴퓨터에서 릴리스 페이지의 그 서버용 이 버전 서버 패키지를 받아 Lyra 데이터 폴더의 server-packages/incoming 폴더에 넣고 다시 연결합니다
「…서버 패키지가 서명 확인을 통과하지 못해 쓰지 않았습니다.」 5분 뒤 다시 연결합니다. 또 실패하면 중간의 프록시나 필터가 파일을 바꾸고 있을 수 있으니 네트워크 관리자에게 알립니다
「…서버 패키지를 이 컴퓨터에서 읽거나 저장하지 못했습니다.」 디스크 공간(서버 종류마다 약 150 MB)을 비우고 Lyra 데이터 폴더를 읽고 쓸 수 있는지 확인한 뒤 다시 연결합니다
「…그 서버는 macOS인데, 이 버전은 macOS 서버를 지원하지 않아…」 Linux나 Windows 서버를 씁니다

lyra-daemon이 데이터 폴더 때문에 시작하지 않을 때

섹션 제목: “lyra-daemon이 데이터 폴더 때문에 시작하지 않을 때”

“… Lyra 데이터 폴더 …를 읽지 못하거나 이 계정의 폴더인지 확인하지 못해 lyra-daemon을 시작하지 않았습니다”가 나옵니다.

  1. 안내에 나온 컴퓨터(이 컴퓨터 또는 서버)로 갑니다.
  2. 안내에 나온 폴더의 소유자와 접근 권한이 지금 쓰는 계정과 맞는지 확인합니다. 폴더는 안내 문장에 적혀 있습니다.
  3. 고친 뒤 다시 시작합니다.

머신 ID(컴퓨터를 구별하는 번호) 문제로 나오는 경우도 있습니다.

  • 없다고 나오면 그 컴퓨터의 관리자에게 만들어 달라고 하고 다시 연결합니다. systemd를 쓰는 Linux에서는 관리자가 sudo systemd-machine-id-setup을 실행합니다.
  • 형식이 잘못되었다고 나오면 관리자에게 다시 만들어 달라고 합니다.
  • 읽을 수 없다고 나오면 그 메시지를 Lyra 담당자에게 전합니다.

업데이트가 끝나지 않았을 때

섹션 제목: “업데이트가 끝나지 않았을 때”

두 가지 모습이 있습니다.

  • 이전 lyra-daemon은 끝났지만 업데이트를 마치지 못함 — 그 컴퓨터의 lyra-daemon 작업은 지금 쓸 수 없습니다. 터미널에서 돌던 에이전트는 계속 돕니다.
  • 전환 결과를 확인하지 못함 — 앱을 닫았다 다시 열고 설정 → 앱 → 버전 정보의 지금 버전을 확인합니다. 같은 안내가 계속 나오면 문제 알리기를 보세요.

앱이 안내하는 복구 순서는 이렇습니다.

  1. 새 터미널을 엽니다.
  2. 화면에 나온 lyra update recover … 명령을 --resolution restore-recorded로 실행해 업데이트 전 버전으로 돌아갑니다.
  3. “업데이트가 진행 중”이라서 거절되면 아무것도 바뀌지 않은 것입니다. 지금 돌고 있는 새 버전을 그대로 쓰려면 --resolution finish로 실행하고, 아니면 업데이트가 끝나길 기다린 뒤 다시 실행합니다.
  4. 돌아간 뒤 앱의 다시 확인을 누르거나 자동으로 다시 연결될 때까지 기다립니다.
  5. 업데이트를 다시 하려면 받고 재시작해서 적용을 누릅니다. 이미 맡긴 일을 다시 맡기지는 마세요.
  6. 그 밖의 이유로 거절되면 나온 메시지를 Lyra 담당자에게 전합니다.

업데이트 확인이 프록시 뒤에서 실패할 때

섹션 제목: “업데이트 확인이 프록시 뒤에서 실패할 때”

“새 버전을 확인하지 못했습니다”가 나오고 최신 버전 확인이 끝나지 않으면 회사나 학교 네트워크의 프록시가 원인일 수 있습니다.

Lyra는 HTTPS_PROXY(와 NO_PROXY) 환경 변수를 따릅니다. Windows의 시스템 프록시 설정은 읽지 않습니다. 환경 변수를 바꾼 뒤에는 Lyra를 완전히 끝냈다가 다시 켜야 합니다.

문제 알리기

섹션 제목: “문제 알리기”

문제를 알릴 때는 다음 순서로 하세요.

  1. 설정 → 정보 → 문제 기록에서 해당 기록을 열고 기술 정보 복사를 누릅니다. 복사한 글에는 경로, 환경 값, 비밀, 명령이 가려져 있습니다.
  2. 필요하면 로그 폴더 열기로 로그 폴더를 열어 main.log를 찾습니다.
  3. 준비한 내용을 Lyra 설치 파일을 받은 저장소의 이슈 페이지에 올립니다.
